Part A · Chapter 7.1

Packages and Crates

The outermost containers — what Cargo builds and distributes

01

What Is a Crate

The smallest amount of code the Rust compiler considers at a time

A crate is the fundamental compilation unit in Rust. Even if you run rustc directly on a single .rs file, the compiler treats that file as a crate. Crates can contain modules, and those modules may live in other files that get compiled together — but the compiler always starts from one crate root and builds outward.

A crate is also the unit of privacy: everything private to a crate is invisible from outside it. When you depend on someone else's library, you can only use what they've marked pub.

🐍 Python comparison

Python doesn't have a direct equivalent. A Python package is a directory with __init__.py, and a module is a single .py file — but there's no compiler enforcing boundaries between them. Rust's crate is more like a compiled library (.so/.dll) with a strict public API surface the compiler checks.

Key takeaway
A crate is the smallest unit the Rust compiler considers — one crate root, one compilation, one privacy boundary.
02

Binary vs Library Crates

Two forms a crate can take

A crate comes in one of two forms:

  • Binary crates compile to an executable. They must have a main function that defines what happens when the program runs. Every cargo run project you've built so far has been a binary crate.
  • Library crates don't have a main function and don't compile to an executable. Instead, they define functionality intended to be shared with multiple projects. The rand crate from Chapter 2 is a library crate — it provides random number generation for any project that depends on it.

When Rustaceans say "crate" without qualification, they usually mean library crate — it's interchangeable with the general concept of a "library."

KindHas main?Compiles toPurpose
Binary crateYesExecutableA runnable program
Library crateNoLibrary (reusable code)Shared functionality for other crates
Key takeaway
Binary crates are executables with main; library crates are reusable code without main. Most projects you depend on are library crates.
03

The Crate Root

Where the compiler starts reading

The crate root is the source file that the Rust compiler starts from. It forms the root module of the crate — everything else branches from it.

By Cargo convention:

  • src/main.rs is the crate root for the binary crate (same name as the package).
  • src/lib.rs is the crate root for the library crate (same name as the package).

Cargo passes the crate root file to rustc, which builds outward from there — following mod declarations into other files as needed.

🐍 Python comparison

Python's closest equivalent is __init__.py — the entry point that defines what a package is. But Rust's crate root is more explicit: the compiler literally starts there and traces every mod statement to build the full module tree. There's no sys.path search, no implicit discovery — just the tree rooted at the crate root.

Key takeaway
The crate root (src/main.rs or src/lib.rs) is where the compiler starts. Everything in the crate branches from this one file.
04

What Is a Package

A bundle of crates described by Cargo.toml

A package is a bundle of one or more crates that provides a set of functionality. It contains a Cargo.toml file that describes how to build those crates. Cargo itself is a package — it contains a binary crate (the cargo command) and a library crate (the logic it uses internally).

The rules are simple:

  • A package can contain at most one library crate.
  • A package can contain as many binary crates as you like.
  • A package must contain at least one crate (library or binary).
Key takeaway
A package is one Cargo.toml + one or more crates. At most one library, unlimited binaries, at least one of either.
05

Cargo Conventions

How Cargo maps files to crates — no configuration needed

Cargo uses file naming conventions to discover crates automatically:

$ cargo new my-project
     Created binary (application) `my-project` package
$ ls my-project
Cargo.toml
src
$ ls my-project/src
main.rs

Cargo looks at the package directory and follows these rules:

Cargo crate discovery
  1. src/main.rs → binary crate named after the package
  2. src/lib.rs → library crate named after the package
  3. src/bin/*.rs → each file is a separate binary crate

If a package contains both src/main.rs and src/lib.rs, it has two crates with the same name — a binary and a library. The binary can use the library as a dependency (just like an external project would).

Multiple binary crates go in src/bin/ — each file becomes a separate executable. For example, src/bin/server.rs compiles to a binary named server.

Key takeaway
src/main.rs = binary, src/lib.rs = library, src/bin/*.rs = extra binaries. Cargo discovers all of these by convention — no Cargo.toml changes needed.

Modules and Paths

Organizing code within a crate and navigating the module tree

06

Modules Cheat Sheet

The quick-reference rules for the entire module system

Before diving into details, here's the complete set of rules. Bookmark this section — you'll refer back to it often.

Module system rules
  1. Start from the crate root — the compiler reads src/lib.rs or src/main.rs first.
  2. Declaring modules — in the crate root, mod garden; tells the compiler to look for code in:
    • Inline: curly brackets after mod garden { ... }
    • The file src/garden.rs
    • The file src/garden/mod.rs (older style)
  3. Declaring submodules — in any other file, mod vegetables; tells the compiler to look in:
    • Inline: curly brackets after the declaration
    • The file src/garden/vegetables.rs
    • The file src/garden/vegetables/mod.rs
  4. Paths to code in modules — once a module is part of your crate, refer to items with paths like crate::garden::vegetables::Asparagus.
  5. Private by default — code within a module is private from its parent. Use pub mod and pub to expose items.
  6. The use keyword — creates shortcuts: use crate::garden::vegetables::Asparagus; lets you write just Asparagus thereafter.

Here's a complete example. The package backyard has this structure:

backyard
├── Cargo.lock
├── Cargo.toml
└── src
    ├── garden
    │   └── vegetables.rs
    ├── garden.rs
    └── main.rs

src/main.rs (the crate root):

use crate::garden::vegetables::Asparagus;

pub mod garden;

fn main() {
    let plant = Asparagus {};
    println!("I'm growing {plant:?}!");
}

src/garden.rs:

pub mod vegetables;

src/garden/vegetables.rs:

#[derive(Debug)]
pub struct Asparagus {}
🐍 Python comparison

This is the equivalent of a Python package: backyard/ with __init__.py, a sub-package garden/ with its own __init__.py, and a module vegetables.py inside it. The key difference: Python's module system is runtime (import searches sys.path), while Rust's is compile-time (the compiler follows mod declarations from the crate root). You can't have "missing module" errors at runtime in Rust — if it compiled, the modules exist.

Key takeaway
mod name; declares a module; the compiler finds it in an inline block, src/name.rs, or src/name/mod.rs. Everything is private by default — use pub to expose.
07

Grouping Related Code in Modules

The mod keyword and the restaurant example

Modules let you organize code within a crate for readability and reuse. They also control privacy: code within a module is private by default, making it an internal implementation detail that outsiders can't touch.

Let's model a restaurant. In the industry, a restaurant has a front of house (where customers are — hosts, servers, bartenders) and a back of house (kitchen, dishwashers, managers). We can mirror that structure with nested modules:

mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
        fn seat_at_table() {}
    }

    mod serving {
        fn take_order() {}
        fn serve_order() {}
        fn take_payment() {}
    }
}

The mod keyword followed by a name declares a module. Its body goes in curly brackets. Inside, you can nest more modules or define functions, structs, enums, constants, traits — any item.

Modules give names to why these functions are related. Programmers navigating the code find hosting and serving grouped logically, rather than scrolling through a flat list of unrelated functions.

Key takeaway
mod name { ... } groups related code and creates a privacy boundary. Use nesting to mirror your domain's real-world structure.
08

The Module Tree

Parent, child, and sibling — the filesystem analogy

The contents of src/main.rs or src/lib.rs form a module named crate at the root of the crate's module tree. Here's the tree for the restaurant example:

Module tree for the restaurant crate
crate
 └── front_of_house
     ├── hosting
     │   ├── add_to_waitlist
     │   └── seat_at_table
     └── serving
         ├── take_order
         ├── serve_order
         └── take_payment

The tree uses the same vocabulary as a filesystem:

  • Parent — the module that contains another. front_of_house is the parent of hosting.
  • Child — a module contained inside another. hosting is a child of front_of_house.
  • Siblings — modules defined in the same parent. hosting and serving are siblings.

And just like a filesystem, you need paths to navigate from one module to another.

🐍 Python comparison

Python's package structure maps directly: a directory is a module with children, files inside are leaf modules, and __init__.py is the parent's body. The difference is that Python's tree is the filesystem itself, while Rust's tree is defined by mod declarations — you can put multiple modules in a single file if you want.

Key takeaway
The module tree starts at crate, branches through mod declarations, and uses parent/child/sibling relationships — just like a filesystem.
09

Absolute vs Relative Paths

Navigating the module tree with ::

To call a function in another module, you need its path — just like a filesystem path, but with :: as the separator:

  • Absolute path — starts from the crate root: crate::front_of_house::hosting::add_to_waitlist()
  • Relative path — starts from the current module: front_of_house::hosting::add_to_waitlist()
mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
    }
}

pub fn eat_at_restaurant() {
    // Absolute path — starts from crate root
    crate::front_of_house::hosting::add_to_waitlist();

    // Relative path — starts from current module
    front_of_house::hosting::add_to_waitlist();
}

Which to use? It depends on what's likely to move. If you move the module and the caller together, relative paths stay valid. If you might move them independently, absolute paths are safer. The Rust team's general preference: absolute paths, because they stay correct when you reorganize.

Why crate:: and not just the module name? crate is the implicit root module of your crate — analogous to / in a filesystem. Starting from crate makes the path unambiguous regardless of where the calling code sits.
Key takeaway
Absolute paths start with crate::, relative paths start from the current module. Both use :: as separator. Prefer absolute when code may move independently.
10

Exposing Paths with pub

Making modules and items public — the privacy rules

In Rust, all items are private to parent modules by default. Items in a parent module can't use private items inside child modules, but child modules can use items in their ancestor modules. This is like the back office of a restaurant: customers can't see in, but staff can see out.

If you try to call add_to_waitlist from outside hosting, you get a compile error:

// error[E0603]: module `hosting` is private
crate::front_of_house::hosting::add_to_waitlist();

Fix it in two steps — make the module public, then make the item public:

mod front_of_house {
    pub mod hosting {           // step 1: module is public
        pub fn add_to_waitlist() {}  // step 2: function is public
    }
}

pub fn eat_at_restaurant() {
    crate::front_of_house::hosting::add_to_waitlist();  // ✅ works
}

Making a module public with pub mod only lets ancestor modules refer to it — it doesn't make the module's contents public. You need pub on each item inside as well. Think of it as two layers of permission: you need the key to the room and the key to the safe inside it.

🐍 Python comparison

Python has no enforced privacy — the underscore convention (_private) is just a gentleman's agreement. In Rust, the compiler prevents you from calling private code. If it compiles, the access is legitimate. If it doesn't, you've found a boundary you need to cross with pub.

Key takeaway
Everything is private by default. Use pub mod to expose a module and pub on each item inside it. Two layers: module + item.
11

Starting Relative Paths with super

Going up to the parent module — like .. in a filesystem

You can construct relative paths that begin in the parent module by using super at the start of the path. This is like starting a filesystem path with ../.

fn deliver_order() {}

mod back_of_house {
    fn fix_incorrect_order() {
        cook_order();
        super::deliver_order();  // go up to parent, then call deliver_order
    }

    fn cook_order() {}
}

super moves up one level in the module tree — from back_of_house to crate — then finds deliver_order there. Use super when a child module is closely related to its parent and you want the path to stay valid even if both move together.

🐍 Python comparison

Python's closest equivalent is relative imports: from .. import deliver_order. Same idea — go up one level. But Python's relative imports are optional and sometimes confusing; Rust's super is the only way to do it, and it's always explicit.

Key takeaway
super:: starts a path from the parent module — use it when a child and its parent are tightly coupled and likely to move together.
12

Struct & Enum Visibility

Field-level and variant-level pub

Making a struct public with pub struct makes the struct name accessible from outside — but its fields stay private unless you mark each one pub individually:

mod back_of_house {
    pub struct Breakfast {
        pub toast: String,           // public — customers choose bread
        seasonal_fruit: String,       // private — chef decides the fruit
    }

    impl Breakfast {
        pub fn summer(toast: &str) -> Breakfast {
            Breakfast {
                toast: String::from(toast),
                seasonal_fruit: String::from("peaches"),
            }
        }
    }
}

Because seasonal_fruit is private, the struct must provide a public constructor (here, summer) — otherwise no one outside the module could create a Breakfast, since they can't set the private field.

Enums are simpler: making an enum public makes all its variants public. No per-variant annotation needed.

mod back_of_house {
    pub enum Appetizer {
        Soup,    // public (because the enum is public)
        Salad,   // public
    }
}

Why the difference? Enums aren't useful unless their variants are accessible — you'd have to annotate every single one otherwise. Structs are often useful with some fields hidden, so the default is private.

💡 Insight — the design reasoning

Structs model data with invariants — rules that must hold. Making fields private lets you enforce those rules through constructors and methods. Enums model choices — the caller needs to know all the options to handle them. Hence: struct fields private by default, enum variants public by default.

Key takeaway
pub struct makes the struct public but its fields stay private (annotate individually). pub enum makes all variants public — no per-variant annotation needed.
13

Binary + Library Best Practice

Keeping the module tree in src/lib.rs and using it from src/main.rs

When a package has both a library crate (src/lib.rs) and a binary crate (src/main.rs), the recommended pattern is:

  • Put the module tree in src/lib.rs.
  • Make the binary crate a thin wrapper that calls into the library.

The binary crate becomes a client of the library — it can only use the public API, just like an external project would. This forces you to design a clean API: you're both the author and a user.

// src/main.rs — thin binary, delegates to the library
use my_project::some_function;

fn main() {
    some_function();
}
This pattern is used extensively in Chapter 12 — the I/O project builds a command-line tool where src/main.rs is just the entry point and all the logic lives in the library crate's public API.
Key takeaway
Define the module tree in src/lib.rs. Make src/main.rs a thin client that uses only the public API. This is both the author and the first user of your API.

Bringing Paths into Scope

The use keyword — creating a local alias for a long path

Writing crate::front_of_house::hosting::add_to_waitlist() every time is tedious. The use keyword creates a shortcut — bring a path into scope once, then use the shorter name everywhere.

use crate::front_of_house::hosting;

pub fn eat_at_restaurant() {
    hosting::add_to_waitlist();  // much shorter
}

Adding use is like creating a symbolic link in the filesystem. After use crate::front_of_house::hosting, the name hosting is valid in the current scope — just as if the module had been defined right here.

Scope matters: use only applies in the scope where it appears. If you move eat_at_restaurant into a child module, the shortcut won't be available there — you'd need to add a use in that module too, or reference it via super::hosting.
🐍 Python comparison

use crate::front_of_house::hosting is the direct equivalent of from backyard.front_of_house import hosting. Same idea, same scope rule. The difference: Python's import happens at runtime and can fail if the module isn't on sys.path; Rust's use is resolved at compile time — if it compiled, the path is valid.

Key takeaway
use path::to::module; creates a local shortcut. It only applies in the scope where it's declared — just like a local variable.
15

Idiomatic use Paths

Functions vs structs/enums — different conventions

Rust has two conventions for use, and the distinction matters for readability:

Item typeIdiomatic useExample
FunctionsBring the parent module into scopeuse std::io; then io::stdin()
Structs, enums, other itemsBring the full path into scopeuse std::collections::HashMap;

For functions, bringing the parent module makes it clear the function isn't defined locally:

// ✅ Idiomatic — parent module in scope
use crate::front_of_house::hosting;
hosting::add_to_waitlist();

// ⚠️ Works, but unclear where add_to_waitlist comes from
use crate::front_of_house::hosting::add_to_waitlist;
add_to_waitlist();

For structs and enums, the full path is preferred:

use std::collections::HashMap;  // ✅ idiomatic
let mut map = HashMap::new();
⚠️ Common mistake — same name conflict 
use std::fmt::Result;
use std::io::Result;   // ❌ error: two `Result` types in the same scope

When two types have the same name, stop the path at the parent module and qualify with the module name: fmt::Result and io::Result.

Key takeaway
Functions: use the parent module. Structs/enums: use the full path. This is convention, not enforced — but following it makes code easier to read.
16

Creating Aliases with as

Renaming imports to avoid name conflicts

When you need two types with the same name in scope, use as to give one a different local name:

use std::fmt::Result;
use std::io::Result as IoResult;

fn function1() -> Result {
    // uses fmt::Result
    Ok(())
}

fn function2() -> IoResult<()> {
    // uses io::Result, aliased to IoResult
    Ok(())
}

This is the cleanest way to handle name collisions — both types keep meaningful names, and the alias reads naturally at the call site.

🐍 Python comparison

Identical to Python's import numpy as np or from typing import Optional as Opt. Same syntax, same purpose. Rust even borrowed the keyword name.

Key takeaway
use path::Type as Alias; renames an import in the current scope — the cleanest fix for name conflicts.
17

Re-exporting with pub use

Reshaping your public API for external consumers

When you bring a name into scope with use, it's private to that scope — external code can't see it. Combining pub and use changes this: the item is brought into scope and re-exported for anyone using your crate.

mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {}
    }
}

pub use crate::front_of_house::hosting;

pub fn eat_at_restaurant() {
    hosting::add_to_waitlist();
}

Without pub use, external code would have to write restaurant::front_of_house::hosting::add_to_waitlist() — and front_of_house would also need to be pub. With pub use, external code can write restaurant::hosting::add_to_waitlist().

This is powerful because it lets you decouple your internal structure from your public API. Organize code however makes sense for development, then use pub use to present a clean surface to consumers. Libraries on crates.io use this extensively.

🐍 Python comparison

The closest Python equivalent is re-exporting from __init__.py: from .hosting import add_to_waitlist inside __init__.py makes it available as restaurant.add_to_waitlist. Same concept — pub use is just more explicit about what's public.

Key takeaway
pub use re-exports an item: brings it into scope and makes it publicly available. Use it to design a clean API that differs from your internal module structure.
18

Using External Packages

crates.io, Cargo.toml, and the standard library

To use an external package, add it to Cargo.toml:

[dependencies]
rand = "0.8.5"

Cargo downloads the package and its dependencies from crates.io and makes them available. Then bring items into scope with use:

use rand::Rng;

fn main() {
    let secret = rand::thread_rng().gen_range(1..=100);
}

The standard library (std) is also an external crate — but it's shipped with Rust, so you don't need to add it to Cargo.toml. You still need use to bring items from it into scope:

use std::collections::HashMap;

The pattern is always the same: declare the dependency in Cargo.toml, then use the items you need.

🐍 Python comparison

Cargo.toml dependencies are Python's requirements.txt or pyproject.toml [dependencies]. crates.io is PyPI. The workflow is identical: declare, install, import. The difference is that Cargo downloads and compiles at build time, while pip installs at setup time and Python imports at runtime.

Key takeaway
Add external crates to Cargo.toml, then use their items. The standard library (std) doesn't need a Cargo.toml entry — it's always available.
19

Nested Paths

Cleaning up long use lists with shared prefixes

When importing multiple items from the same crate or module, you can collapse them into one use statement with nested paths:

// Before — two separate lines with a shared prefix
use std::cmp::Ordering;
use std::io;

// After — nested path with curly brackets
use std::{cmp::Ordering, io};

This reduces vertical space and makes the shared origin obvious. You can nest at any level in the path, which is especially useful when one path is a subpath of another:

// Two lines — one is a subpath of the other
use std::io;
use std::io::Write;

// Merged into one with `self`
use std::io::{self, Write};

Here, self refers to std::io itself — so this single line brings both std::io (as io) and std::io::Write (as Write) into scope.

Key takeaway
use std::{cmp::Ordering, io}; collapses shared-prefix imports into one line. Use self to import the module itself alongside its children.
20

The Glob Operator

Importing everything with *

To bring all public items from a module into scope, use the glob operator:

use std::collections::*;

This imports every public item defined in std::collections — HashMap, BTreeMap, HashSet, etc. — into the current scope.

Glob is convenient but use with caution:

  • It makes it harder to tell what names are in scope and where they came from.
  • If the dependency adds a new public item with the same name as one of yours, you get a collision — and your code breaks when you upgrade.

Two places where glob is acceptable:

  • Testing — bringing everything under test into the tests module (Chapter 11).
  • Prelude patterns — some crates provide a prelude module designed to be glob-imported.
🐍 Python comparison

use std::collections::* is Python's from collections import * — same idea, same downsides. Both are frowned upon in production code for the same reason: namespace pollution and silent collisions. The Rust compiler will catch the collision at build time; Python will surprise you at runtime.

Key takeaway
use path::*; imports all public items. Convenient for testing and preludes, but avoid in general code — it makes names hard to trace and upgrades fragile.
