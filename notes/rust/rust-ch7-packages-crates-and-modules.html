Packages, Crates, and Modules

Python never had to teach you this: the filesystem is your module system, privacy is a naming convention, and import just runs more code. Rust takes the same ideas and hands them to the compiler. This chapter is about three questions — where does my code live, how do I name it, and who can see it — answered in a way you can rely on.

Part A · Chapter 7.1

The Big Picture

What Cargo builds, and the mental model that makes the rest obvious

01

The Mental Model

Rust's module system is Python's — but the compiler enforces it

Here's the framing that makes this whole chapter click. In Python, code organization is really just files and folders. my_package/utils.py is a module because it's a file. my_package/ is a package because it has an __init__.py. _helper is private because we all agreed to ignore it. None of this is enforced — it's convention, and you can break every piece of it without the interpreter batting an eye.

Rust takes the same three ideas and makes them rules the compiler checks:

QuestionPython's answerRust's answer
Where does code live?Filesystem: folders = packages, files = modulesCrates (what compiles) + modules (what you declare)
How do I name things?import paths, sys.pathPaths with ::, starting at crate::
Who can see what?_underscore + __all__ conventionspub, enforced by the compiler
Dependencies?pip + requirements.txtCargo.toml + crates.io
Re-exports?__init__.pypub use

Every section in this chapter answers one of those three questions. If you hold onto the mapping table above, the details stop being random syntax.

🐍 Why Python never taught you this 
# A typical Python package — all convention, none enforced
my_package/
├── __init__.py          # curates the public API
├── _internal.py         # "private" — but importable by anyone
└── utils.py

# Nothing stops you:
from my_package._internal import _secret   # works, every time

# __all__ only affects `import *`, not direct imports
__all__ = ["public_api"]

In Python you can break every rule and nothing happens. In Rust, breaking a rule is a compile error. That sounds like restriction — but it's the compiler being on your side. Conventions get violated by accident; rules don't. Python trusts you, Rust verifies you.

Key takeaway
Rust organizes code with the same ideas as Python — packages, modules, imports, visibility — but the compiler enforces them. Nothing is convention; everything is a rule you can rely on.
02

Crates — What Gets Compiled

The unit of compilation, and the unit of privacy

A crate is what the compiler actually builds: one root file — the crate root — plus everything that root declares, and nothing else. It's the boundary of a whole program or library.

There are two kinds, and the difference is one question: does it have a main?

Binary crateLibrary crate
main?YesNo
Compiles toAn executable you can runCode others can use
Sounds likeA programA library

One subtle thing: a crate is also a privacy boundary. Items are private to their crate unless marked pub — so even when another crate depends on yours, it can only see the surface you exposed. There is no "just reach in and grab it."

And a vocabulary note: when a Rustacean says "crate" without qualification, they almost always mean library crate. "Add this crate" = "add this library."

🐍 The Python parallel

Python has no equivalent unit. Your program is just files importing each other; the distribution unit is a wheel, the import unit is a module, and there's no enforced boundary anywhere. A Rust crate is closer to a compiled shared library (.so/.dll): a bundle of code with a strictly enforced public interface. Python's "public API" is a hope; Rust's is a compiled fact.

Key takeaway
A crate is the unit of compilation and the unit of privacy: one root file, one boundary. Binary crates run, library crates are shared — and nothing outside a crate sees past its pub surface.
03

Packages & Cargo's Conventions

One Cargo.toml, up to one library, any number of binaries

A package is what Cargo builds: one Cargo.toml plus the crates it describes. The rules are few:

  • At most one library crate — it carries the package's public name on crates.io.
  • As many binary crates as you want.
  • At least one crate of either kind.

Cargo doesn't ask you to declare what crates exist — it infers them from filenames:

$ cargo new bookcrate
     Created binary (application) `bookcrate` package
$ tree src
src
└── main.rs          ← binary crate named `bookcrate`
Cargo's discovery rules
  1. src/main.rs → a binary crate named after the package
  2. src/lib.rs → a library crate named after the package
  3. src/bin/*.rs → each file becomes its own binary crate

That gives you the classic project shape: all real logic in src/lib.rs, and a src/main.rs so thin it's almost embarrassing — it parses args, calls the library, and exits. The library is testable and shareable; the binary is just a front door.

🐍 Python comparison — entry points 
# Python declares its entry points explicitly, in pyproject.toml
[project.scripts]
bookcrate = "bookcrate.cli:main"

# Rust just... puts a file in the right place
# src/main.rs → done, Cargo found it.

Python makes you declare entry points; Rust makes you place files. Convention over configuration — fewer things to forget, fewer typos that fail silently at install time.

Key takeaway
A package = one Cargo.toml + ≤1 library crate + any number of binaries. Cargo discovers crates by filename, not config. Keep logic in the library, keep the binary thin.

04

Declaring Modules

The tree exists only where you say it does

Inside a crate, a module is a named group of items — functions, structs, other modules. Declare one with mod, and nest them to mirror your domain. Say we're building bookcrate, a library catalogue:

mod inventory {
    mod search {
        fn by_author() {}
        fn by_title() {}
    }

    mod register {
        fn add_book() {}
        fn remove_book() {}
    }
}

mod lending {
    fn check_out() {}
    fn return_book() {}
}

This creates a module tree — the compiler's map of your crate:

The module tree — think folders, but declared in code
crate                     ← the root (src/lib.rs or src/main.rs)
 ├── inventory
 │   ├── search
 │   │   ├── by_author
 │   │   └── by_title
 │   └── register
 │       ├── add_book
 │       └── remove_book
 └── lending
     ├── check_out
     └── return_book

The vocabulary is the same as folders: inventory is the parent of search; search and register are siblings; by_author is a child of search.

But here's the crucial difference from Python: the tree exists only where you declare it. In Python, hosting/waitlist.py exists because it's on disk. In Rust, a file on disk is nothing until some mod declaration pulls it in. And the flip side: Rust modules don't need files at all — several small modules can share one file, which Python can't do.

⚠️ Common mistake — the orphan file 
// You created src/hosting.rs, filled it with working code...
// ...and src/main.rs never got `mod hosting;`.
//
// Result: NO error. The compiler simply ignores the file.
// Your function "exists" on disk and nowhere else.

// Fix: declare it in the crate root:
mod hosting;   // ← in src/main.rs or src/lib.rs

This is the #1 confusion for Python developers, where import finds files by magic. In Rust you must declare every module. An undeclared file compiles silently into nothing.

Key takeaway
mod name { ... } declares a module and its tree position. The tree is declared, not mirrored from the filesystem — orphans are invisible, and modules don't require files.
05

One Module per File

Splitting code across files without losing the tree

Inline modules are fine when they're small, but files get long. Moving a module to its own file is a one-character change: swap the curly brackets for a semicolon.

// Before — inline, in src/lib.rs
mod inventory {
    pub fn count() -> u32 { 0 }
}

// After — declared, in src/lib.rs
mod inventory;

// The compiler looks for the code in, in order:
//   1. src/inventory.rs        ← new style, preferred
//   2. src/inventory/mod.rs    ← old style

Submodules work the same way, one level at a time. Inside inventory.rs you can write mod search; — the compiler finds src/inventory/search.rs.

bookcrate's file layout
src/
├── lib.rs              ← declares: mod inventory; mod lending; pub use ...
├── inventory.rs        ← declares: mod search; mod register;
├── inventory/
│   ├── search.rs       ← by_author(), by_title()
│   └── register.rs     ← add_book(), remove_book()
├── lending.rs          ← check_out(), return_book()
└── main.rs             ← the thin binary front door

Why the new style wins: every module gets a unique filename. With mod.rs, deeply nested projects fill up with files all literally named mod.rs — confusing in editors and diffs alike.

🐍 Python comparison — the filesystem mismatch 
# Python: directory structure IS module structure, always
inventory/
├── __init__.py
├── search.py
└── register.py

# Rust: the tree is declared first; files serve it
# lib.rs says "mod search;", search.rs just contains the code

Python's layout is fixed by the filesystem — renaming a file renames the module, and every folder needs an __init__.py. Rust separates the two: the tree lives in mod declarations, and files are just where the code happens to be. Move code between files and the tree doesn't change.

Key takeaway
mod name; tells the compiler to find the module's code in name.rs (preferred) or name/mod.rs. Declare submodules inside each file, one level at a time.
06

Paths — Naming Things

How to reach any item in the tree, with ::

Once you have a tree, you need to name things in it. A path is a list of names joined by :: — like a file path, but with two colons instead of slashes.

There are two kinds:

  • Absolute — starts at the crate root with crate::: crate::inventory::search::by_author()
  • Relative — starts from the current module: inventory::search::by_author(), or super:: to go up one level
mod inventory {
    pub mod search {
        pub fn by_author() {}
    }
}

fn main() {
    // Absolute — explicit about where it starts
    crate::inventory::search::by_author();

    // Relative — starts from wherever we are (crate root, here)
    inventory::search::by_author();
}

When to use which: if you move the item and its callers together, relative paths survive the move; if they move independently, absolute paths stay correct. That's why most real Rust code defaults to absolute paths — they read like a map and don't care where you're standing.

super:: is the one relative path you'll see often: it goes up one level, exactly like .. in a shell or a Python relative import. Use it when a child module is tightly coupled to its parent and they'd move together.

🐍 Python comparison — same two kinds 
# Python absolute (PEP 8 prefers this)
from my_package.inventory.search import by_author

# Python relative
from .inventory.search import by_author   # . = current, .. = parent

Nearly identical concepts. Rust's crate:: is Python's absolute import; super:: is Python's ... The practical difference: Python's relative imports are fragile enough that many teams ban them with linters. Rust's are precise and checked — the compiler tells you the moment a relative path stops resolving.

⚠️ Common mistake — the right path, wrong permission 
// error[E0603]: module `search` is private
crate::inventory::search::by_author();

// The path is PERFECT. The module just isn't pub.
// In Python this never happens: right path ⇒ import works.
// In Rust, a correct path is only half of it.
// Fix: see the next section — `pub`.

This error shocks every Python developer once. You spelled everything right and it still fails — because in Rust, having the right address and having permission are two separate checks.

Key takeaway
Paths name items in the tree: crate:: is absolute from the root, super:: goes up one level, relative paths start where you stand. A correct path to a private item still fails — path and permission are separate checks.
07

Privacy & pub — The Wall

The single biggest mental shift from Python

This is the section that changes how you write code forever.

In Rust, everything is private by default. An item is visible to its parent module and its descendants — think of it like an employee who can see the whole org chart above them but whose own department's internals aren't visible from outside. Code inside a module can use anything in its ancestors; code outside cannot see in at all.

To open a door, you use pub — and you need two keys:

mod inventory {
    pub mod search {              // key 1: the module is public
        pub fn by_author() {}    // key 2: the function is public
    }
}

Making the module public says "this exists." Making the item public says "you can use this." Both are required, and the split is deliberate: you can have a public module whose contents are all private — an open door with a locked register.

💡 Insight — why two layers?

Because the two promises have different costs. Making a module public promises "this will keep existing" — cheap; you can restructure everything inside it and nobody notices. Making a function public promises "this signature is stable" — expensive; changing it breaks every caller. Splitting the two lets you say: "the shape of my library is stable, its guts are my business." Libraries evolve internal structure freely and only ever guarantee the thin pub surface.

🐍 Python comparison — convention vs wall 
# Python — everything is public unless you play nice
from my_package import _secret    # works. nothing stops you.

# __all__ restricts only `import *`
__all__ = ["public"]
from my_package import _secret    # STILL works. __all__ is bypassable.

Python's _underscore and __all__ are gentle suggestions. Rust's compiler physically blocks access to non-pub items — if it compiles, the access is legitimate. The underscore convention goes from "please don't" to "you cannot," and that's a gift: you stop defending conventions and start trusting them.

Key takeaway
Everything is private by default; children see ancestors, outsiders see nothing. pub mod makes the module visible, pub on the item makes it usable — both keys required, and the compiler enforces it.
08

Struct & Enum Visibility

Why fields and variants have different rules

Making a struct pub exposes the name — but each field stays private unless you mark it pub individually. That looks like busywork until you see what it buys you: invariants.

mod lending {
    pub struct Loan {
        pub book_title: String,     // public — fine to read/write
        due_date: u32,              // private — rules live here
    }

    impl Loan {
        pub fn new(title: &str) -> Loan {
            Loan { book_title: String::from(title), due_date: 0 }
        }
        pub fn extend(&mut self, days: u32) {
            self.due_date += days;   // the ONLY way to change due_date
        }
    }
}

Because due_date is private, the only way to touch it is through Loan's methods. You can enforce "due dates can never go backwards" in exactly one place, and the compiler guarantees nobody sneaks around it. In Python, this is a property + hope; in Rust it's a field marker + certainty.

Enums are the opposite: make the enum pub and all its variants become public automatically.

pub enum BookStatus {
    Available,      // public, automatically
    OnLoan,         // public, automatically
    Discarded,      // public, automatically
}

Why the difference? Enums are choices, and matching on an enum requires knowing every case. A private variant would be unhandleable — your match couldn't cover it. Structs are data with rules; hiding fields is what protects the rules. Different jobs, different defaults.

🐍 Python comparison — no enforced field privacy 
from dataclasses import dataclass

@dataclass
class Loan:
    book_title: str
    due_date: int = 0

loan = Loan("The Left Hand of Darkness")
loan.due_date = -100   # Python: fine. Your invariant: broken.

A Python dataclass makes every field publicly assignable; protecting one means writing a property with a setter — opt-in boilerplate you must remember. Rust's per-field pub is the default shape: public by exception, protected by default.

Key takeaway
pub struct = public name, private fields (mark each). pub enum = public name, all variants public. Structs hide fields to protect invariants; enums expose every choice so match can handle them all.

09

use — Local Shortcuts

A naming shortcut that costs nothing and runs nothing

Paths are precise, and precise paths are long. use brings a path into scope under a short local name — think of it as a symbolic link, or Python's from x import y:

use crate::inventory::search;

fn main() {
    search::by_author("Ursula K. Le Guin");   // instead of the full path, every time
}

Two things Python developers get wrong about use, so here they are up front:

  • It's not "load." Python's import executes the module — top-level code runs, side effects happen, and you can break things by importing at the wrong moment. Rust compiled your whole crate already. use is purely a naming shortcut: zero runtime cost, zero side effects, it could not possibly fail at runtime.
  • It's scoped like a local variable. Declare it at the top of a function and it's only valid there. Move code into a child module and the shortcut doesn't follow — the new scope needs its own use.
🐍 Python comparison — import runs code, use doesn't 
# Python — importing executes the module
# logging.py: print("imported!")   ← runs on import!
import logging    # side effects happen right here

# Rust — use is a compile-time alias
use std::io;     # nothing runs. it's just a name.

Python modules can (and often do) run code at import time; import order matters and circular imports are a real disease. In Rust, use resolves names at compile time — no execution, no ordering hazards, no circular-import errors. Ever.

Key takeaway
use creates a scoped, compile-time shortcut. It doesn't load or run anything — everything is already compiled. Move code, and the shortcut stays behind with its old scope.
10

Idiomatic use

Functions: import the parent. Types: import the item.

Two conventions keep use statements readable, and they differ by what you're importing:

WhatIdiomaticWhy
FunctionsImport the parent moduleKeeps the call clearly namespaced
Structs / enumsImport the item itselfThe name is the type — short is fine
// ✅ Functions — bring in the module, call through it
use crate::inventory::search;
search::by_author("Borges");       // clearly not a local function

// ✅ Types — bring in the type directly
use std::collections::HashMap;
let mut index = HashMap::new();

// ⚠️ Works, but reads wrong
use crate::inventory::search::by_author;
by_author("Borges");               // looks local. misleads the reader.

These are conventions, not rules — the compiler accepts both. But conventions exist because a bare by_author(...) call gives your reader no hint where it came from, and readability is the whole point of use.

⚠️ Common mistake — two imports, same name 
use std::fmt::Result;
use std::io::Result;    // ❌ error[E0255]: name `Result` defined multiple times

// Python silently shadows the first import — bugs hide.
// Rust refuses to guess which one you meant.
// Fix: import the parents (fmt::Result / io::Result), or alias (next section).

Python lets the last import win and you find out months later. Rust stops you at compile time. Annoying once, correct forever.

Key takeaway
Functions: use the parent module. Structs/enums: use the item itself. Convention, not law — but it keeps call sites honest about where names come from.
11

Aliases with as

Renaming an import to dodge a collision

When two legitimately useful names collide, as renames one — locally, in the current scope:

use std::fmt::Result;
use std::io::Result as IoResult;   // both live side by side now

fn format_something() -> Result { /* fmt::Result */ }
fn read_file() -> IoResult<()> { /* io::Result */ }
🐍 Python comparison — same keyword 
import numpy as np
from typing import Optional as Opt

# Rust borrowed the keyword verbatim:
use std::io::Result as IoResult;

Identical idea, identical keyword. If you can write import numpy as np, you already know this section.

Key takeaway
use path::Thing as LocalName; renames an import in the current scope — the clean fix when two names collide.
12

pub use — Re-exporting

The __init__.py story, with a wall around it

A plain use is a private shortcut — only the scope that declares it can use it. pub use does the same thing and makes the name publicly available to everyone using your crate. That's a re-export.

mod inventory {
    pub mod search {
        pub fn by_author() {}
    }
}

// Re-export: consumers now reach it at the crate root
pub use inventory::search;

// Consumers write:   bookcrate::search::by_author()
// Instead of:        bookcrate::inventory::search::by_author()

Think warehouse versus shop floor. Internally you store things in deep, logical aisles. Publicly, you put the handful of things customers actually need on a front shelf. pub use moves items to the front shelf — without moving them in the warehouse. Your internal structure can be deep and messy; your public API can be flat and clean.

💡 Insight — pub use is curation

Real libraries lean on this heavily. A crate's internal module tree might be 4 levels deep, but its public surface is often a single short list of names at the crate root — everything consumers need, nothing else. That's the API design difference between "the code is organized" and "the library is pleasant to use." You organize for yourself; you curate for your users.

🐍 Python comparison — the __init__.py story 
# __init__.py — Python's re-export ritual
from .inventory.search import by_author

# Users can now do the short import.
from my_package import by_author

# ...but they can ALSO bypass it entirely:
from my_package.inventory.search import by_author  # always works

Same idea, different teeth. Python's __init__.py re-exports are a convenience — consumers can always bypass them with a deep import. Rust's pub use is the only door: what you re-export is what exists, and the compiler enforces it.

Key takeaway
pub use re-exports: a shortcut that's also public. Decouple your internal structure from your public API — organize for yourself, curate for your users.
13

External Packages

crates.io, Cargo.toml, and why there's no "works on my machine"

Almost no project is only your code. Rust's package registry is crates.io, and Cargo is pip, the install step, and the build step in one tool. To use someone else's crate, declare it:

# Cargo.toml
[dependencies]
serde = { version = "1", features = ["derive"] }

cargo build downloads, compiles, and wires up everything — including transitive dependencies. Then use brings its items into scope, exactly like your own modules:

use serde::Serialize;

#[derive(Serialize)]
struct Book { pub title: String }

Two things worth knowing:

  • No separate install step. Declare, build, done. And Cargo.lock pins exact versions, so "it compiled for me" means "it compiles for you."
  • std is always there. The standard library ships with Rust — no Cargo.toml entry needed. It still needs a use to bring names into scope: use std::collections::HashMap;
🐍 Python comparison — pip vs Cargo 
# Python: three moving parts
# 1. requirements.txt:  numpy==1.26
# 2. shell:             pip install -r requirements.txt
# 3. code:              import numpy

# Rust: declare, and cargo does the rest
# 1. Cargo.toml:        rand = "0.8"
# 2. cargo build        ← downloads + compiles + locks versions
# 3. code:              use rand::Rng;

Same ideas, fewer failure modes. Python splits the job across requirements files, a virtual environment, and an install command that can silently succeed on a stale environment. Rust fuses them: the manifest, the resolution, and the build are one flow, and the lockfile makes it reproducible.

Key takeaway
Add external crates to Cargo.toml, then use their items. Cargo handles download, compile, and version pinning. std needs no declaration — just a use.
14

Nested Paths & Glob

Collapsing long import lists, and the one tool to use sparingly

When several imports share a prefix, collapse them with curly brackets — a nested path:

// Before — the shared prefix repeats
use std::cmp::Ordering;
use std::io;

// After — one line
use std::{cmp::Ordering, io};

// When one import IS a subpath of another, `self` names the module itself
use std::io;
use std::io::Write;
// ↓ collapses to
use std::io::{self, Write};

The other tool is the glob: use path::*; imports every public item.

use std::collections::*;   // HashMap, BTreeMap, HashSet... everything

Glob is convenient and it's a trap in general code: you can't tell where a name came from, and a dependency upgrade can suddenly make a name ambiguous. Two places where it's genuinely fine:

  • Tests — bringing everything under test into the test module.
  • Preludes — crates that ship a prelude module explicitly designed to be glob-imported.
⚠️ Common mistake — the glob that breaks on upgrade 
use crate_a::*;
use crate_b::*;

// Works today. Then crate_a 1.2 adds a public `Config` type,
// crate_b already had one, and suddenly:
// error[E0659]: `Config` is ambiguous
//
// Python: silent shadowing, bugs later.
// Rust: loud error now — but it still breaks your build.

This is why glob imports make upgrades fragile. The compiler will tell you about the collision, but it's you who has to go find the two Configs and disambiguate them.

🐍 Python comparison — identical risk 
# Python's `from x import *` is Rust's glob — same idea, same risk
from os.path import *
from shutil import *

Both communities reached the same verdict: glob is for tests and preludes, not production code. The one difference — Rust detects collisions at compile time instead of silently shadowing.

Key takeaway
Nested paths (use std::{cmp::Ordering, io};) collapse shared prefixes; self names the module itself. Glob imports everything — reserve it for tests and preludes.
