Part A · Chapter 7.1

Packages and Crates

The outermost containers — what Cargo builds and what you distribute

01

Crates — Compilation Units

The boundary the compiler draws around a chunk of code

Up to now, everything lived in one .rs file. That works for learning, but real projects grow. Before you can split code across files, you need to understand what the compiler treats as "one thing."

That unit is the crate. When you run cargo build, the compiler starts at one file — the crate root — and follows every mod declaration outward to gather all the code that belongs together. Everything it collects is one crate. Everything outside that crate is invisible unless explicitly marked pub.

A crate comes in two flavours:

Binary crateLibrary crate
Has main?YesNo
Compiles toAn executableReusable code (no .exe)
ExampleYour CLI toolThe rand crate from Chapter 2

When Rustaceans say "crate" without qualification, they almost always mean library crate — it's their word for "library."

🐍 The Python parallel 
# Python — no single "crate" concept
my_project/
├── __init__.py      # makes it a package
├── utils.py         # a module
└── main.py          # the entry point

# Any file can import any other — no enforced boundary.
# `__all__` in __init__.py is a suggestion, not a wall.
from my_project.utils import helper  # always works, even if you didn't intend it

Python has packages and modules, but nothing that maps to a "crate." A Python package is a directory; a module is a .py file. There's no compiler enforcing what's public — _private names are a gentleman's agreement, not a wall. A Rust crate is more like a compiled .so/.dll with a strict public API surface that the compiler checks. If it compiles, the access is legitimate. If it doesn't, you've hit a real boundary.

Key takeaway
A crate is what the compiler builds: one root file, one privacy boundary. Binary crates have main; library crates don't and are meant to be shared.
02

Binary vs Library Crates

One runs, the other is imported — and the same package can have both

A binary crate is a program you can run — cargo run executes its main. A library crate is code you import — it has no main, it just defines things for others to use.

Most real projects have both. The binary crate is thin — just enough to start the program — and it calls into the library crate for the actual logic. This pattern exists because:

  • The library crate can be shared: other projects (and your own tests) can depend on it.
  • The binary crate is a client of your library, which forces you to design a clean API.
// src/lib.rs — the library crate (reusable logic)
pub fn run(config: Config) {
    // ... all the real work ...
}

// src/main.rs — the binary crate (thin wrapper)
use my_app::run;
use my_app::Config;

fn main() {
    let config = Config::from_args();
    run(config);
}
🐍 Python comparison 
# Python has the same pattern, but it's a convention, not enforced
my_app/
├── __init__.py      # exports: from .core import run, Config
├── core.py          # the real logic
└── __main__.py      # python -m my_app → thin entry point

# __main__.py
from .core import run, Config
config = Config.from_args()
run(config)

Python's __main__.py is the binary crate; the package itself is the library. The difference: Python won't stop you from importing internals (from my_app.core import _helper), while Rust's compiler will. Also, Python's __init__.py has to manually re-export what you want public; Rust's pub on the item itself handles that.

Key takeaway
A single package can have both a library and a binary crate. Keep the real logic in the library; make the binary a thin wrapper that calls into it.
03

The Package — Cargo's Container

One Cargo.toml, one or more crates

A package is the thing cargo build actually builds. It's described by Cargo.toml and bundles one or more crates. The rules are minimal:

  • At most one library crate.
  • As many binary crates as you like.
  • At least one crate of either kind.

Cargo itself is a package — it has a binary crate (cargo the command) and a library crate (the logic the binary calls).

🐍 Python comparison

A Python package is a directory with __init__.py. There's no concept of "at most one library" — you can have as many modules as you want, all at the same level. Rust's restriction exists because the library crate name becomes the package's public identity on crates.io. One name, one library. Binaries are internal.

Key takeaway
A package = one Cargo.toml + one library crate (at most) + binary crates (unlimited) + at least one of either.
04

Cargo File Conventions

How Cargo discovers crates without any configuration

Cargo uses file names to decide what crates exist. You don't tell it in Cargo.toml — it just knows:

$ cargo new my-project
     Created binary (application) `my-project` package
$ ls my-project/src
main.rs
Cargo's discovery rules
  1. src/main.rs → binary crate named after the package
  2. src/lib.rs → library crate named after the package
  3. src/bin/*.rs → each file is a separate binary crate

So a package with both src/main.rs and src/lib.rs has two crates with the same name — a binary and a library. The binary can use the library just like any external dependency would.

🐍 Python comparison 
# Python has no equivalent discovery — you define entry points explicitly
# pyproject.toml
[project.scripts]
my-tool = "my_package.cli:main"  # you must declare this

# Rust: just put the file in the right place. Cargo finds it.

Python's pyproject.toml requires you to declare entry points explicitly. Cargo's convention-over-configuration approach means you just place files in the right location — no Cargo.toml edits needed for the basic binary/library split.

Key takeaway
src/main.rs = binary, src/lib.rs = library, src/bin/*.rs = extra binaries. Cargo discovers all of these by filename convention.

Splitting code within a crate and controlling who can see what

05

Modules — Privacy and Structure

The mod keyword creates a named group with a privacy wall around it

A crate can have hundreds of functions, structs, and enums. Without organization, it's a junk drawer. Modules give you two things at once: names (so related code is grouped) and privacy (so internals stay internal).

Define a module with mod and curly brackets. Nest them to mirror your domain:

mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
        fn seat_at_table() {}
    }

    mod serving {
        fn take_order() {}
        fn serve_order() {}
        fn take_payment() {}
    }
}

This creates a module tree — the compiler's view of your crate's structure:

The module tree — like a filesystem
crate                     ← the root (src/lib.rs or src/main.rs)
 └── front_of_house       ← a module
     ├── hosting           ← child of front_of_house
     │   ├── add_to_waitlist
     │   └── seat_at_table
     └── serving           ← sibling of hosting
         ├── take_order
         ├── serve_order
         └── take_payment

The vocabulary is the same as a filesystem: front_of_house is the parent of hosting; hosting and serving are siblings; add_to_waitlist is a child of hosting.

Where does the compiler look for module code?

When you write mod hosting; (with a semicolon, no curly brackets), the compiler searches for the code in these locations, in order:

Module file resolution
  1. Inline: mod hosting { ... } — curly brackets right there in the parent file
  2. New style: src/front_of_house/hosting.rs — a file named after the module
  3. Old style: src/front_of_house/hosting/mod.rs — the mod.rs convention

The new style (module_name.rs) is preferred because it keeps all filenames unique and avoids the mod.rs clutter that stacks up when you have many nested modules.

🐍 The full Python parallel 
# Python's package structure IS the module tree
front_of_house/
├── __init__.py
├── hosting/
│   ├── __init__.py
│   └── waitlist.py        # add_to_waitlist() lives here
└── serving/
    ├── __init__.py
    └── orders.py

# In __init__.py you manually re-export:
from .hosting.waitlist import add_to_waitlist

# Importing works like this:
from front_of_house.hosting.waitlist import add_to_waitlist

In Python, the module tree is the filesystem. In Rust, the module tree is defined by mod declarations — you can put multiple modules in one file if you want. This gives Rust more flexibility: a small module doesn't need its own file, you can just write mod hosting { ... } inline. Python requires a file per module, no exceptions.

The privacy difference is the big one. In Python, nothing stops you from doing from front_of_house.hosting._internal import _secret — the underscore is just a hint. In Rust, the compiler physically prevents you from reaching private items. If it compiled, the access is legitimate.

⚠️ Common mistake — forgetting mod in the crate root 
// You created src/hosting.rs and wrote code in it.
// But src/main.rs doesn't have `mod hosting;`
//
// Result: the compiler doesn't know hosting exists.
// No error about missing code — it just ignores the file entirely.
//
// Fix: add `mod hosting;` to src/main.rs (or src/lib.rs).

This is the #1 confusion for people coming from Python, where import finds the file automatically. In Rust, you must declare every module. A file sitting in src/ with no mod declaration is invisible to the compiler — it's as if it doesn't exist.

Key takeaway
mod name; declares a module and tells the compiler to find its code. Everything inside is private by default. You must declare every module — orphan files are invisible.
06

Paths — Navigating the Module Tree

Absolute (crate::) and relative paths, separated by ::

To call a function in another module, you need its path — just like typing a file path in your terminal, but with :: as the separator.

Two kinds:

  • Absolute path — starts from the crate root: crate::front_of_house::hosting::add_to_waitlist()
  • Relative path — starts from the current module: front_of_house::hosting::add_to_waitlist()
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {}
    }
}

pub fn eat_at_restaurant() {
    // Absolute — starts from crate root
    crate::front_of_house::hosting::add_to_waitlist();

    // Relative — starts from current module (crate root here)
    front_of_house::hosting::add_to_waitlist();
}

Which to prefer? If you move the definition and the caller together (say, into a new parent module), relative paths stay valid. If you move them independently, absolute paths stay correct. The Rust team generally prefers absolute paths for this reason.

🐍 Python comparison 
# Python's absolute import (preferred by PEP 8)
from my_package.front_of_house.hosting import add_to_waitlist

# Python's relative import
from .front_of_house.hosting import add_to_waitlist

Same two kinds! Python's absolute imports start from the top-level package name; relative imports start with . (one dot = current package, .. = parent). The parallel is almost exact — Rust's crate:: is Python's absolute path, and Rust's module-relative path is Python's . import. The difference: Python's relative imports are optional and sometimes confusing; Rust's paths are the only way to name things, and they're always explicit.

⚠️ Common mistake — paths fail because modules are private 
// error[E0603]: module `hosting` is private
crate::front_of_house::hosting::add_to_waitlist();

// The path is CORRECT. But the module isn't public.
// Having the right path doesn't mean you have permission.
// Fix: make the module AND the function `pub` (see next section).

This is a key difference from Python: in Rust, a correct path to a private item is a compile error. In Python, a correct import of a private name works fine — the underscore is just a hint.

Key takeaway
Absolute paths start with crate::; relative paths start from the current module. Both use ::. A correct path to a private item is still a compile error — privacy and path are separate checks.
07

Exposing Code with pub

Opening the privacy doors — it takes more than one key

In Rust, everything is private to its parent module by default. Children can see their ancestors (a function inside hosting can use items from front_of_house), but parents can't see into their children. This is the back-office rule: staff can see the whole restaurant, customers can't see the kitchen.

To let code outside a module in, you need pub. But here's the catch: making a module public doesn't make its contents public. You need two keys:

// Step 1: make the module public (so outsiders can see `hosting` exists)
// Step 2: make the item public (so outsiders can call add_to_waitlist)
mod front_of_house {
    pub mod hosting {                    // key 1: module is public
        pub fn add_to_waitlist() {}      // key 2: function is public
    }
}

This two-layer design is deliberate. Making the module public says "this exists." Making the item public says "you can use this." You can have a public module with private items — that's the restaurant with an open door but a locked cash register.

🐍 Python comparison 
# Python — everything is public unless you use underscores
from front_of_house.hosting import add_to_waitlist  # always works

# The "privacy" convention:
_helper()       # single underscore = "please don't import this"
__secret()      # double underscore = name-mangled, but still importable

# __all__ in __init__.py can restrict `from package import *`
__all__ = ["add_to_waitlist"]  # only this is exported on `import *`
# But direct imports still bypass __all__!

Python's __all__ is the closest thing to Rust's pub, but it only affects from package import *. Direct imports (from package import _secret) still work. Rust's compiler physically blocks access to non-pub items — it's not a convention, it's a wall. If it compiles, the access is legitimate.

💡 Insight — why the two-layer design?

Consider a module that's public (pub mod hosting) but has all private functions. What can external code do? It can name the module — use crate::front_of_house::hosting — but it can't call anything inside. That seems useless, but it matters for documentation and for future expansion. You're saying "this module exists and you can depend on its existence, but its internals are mine to change." As you evolve the library, you can selectively pub functions without reorganizing the module structure.

Key takeaway
Everything is private by default. pub mod makes the module visible; pub on the item makes it usable. Both are needed — visibility and usability are separate permissions.
08

Going Up with super

Relative paths that start from the parent — like ../ in a shell

super at the start of a path goes up one level in the module tree, just like ../ in a filesystem. Use it when a child module is tightly coupled to its parent and you want to move them together someday without updating paths.

fn deliver_order() {}

mod back_of_house {
    fn fix_incorrect_order() {
        cook_order();
        super::deliver_order();  // up to parent, then find deliver_order
    }

    fn cook_order() {}
}

Think of it as the chef calling the front desk: "I need someone to deliver this order." The chef doesn't know the delivery person's full organizational path — they just go up one level to the parent department.

🐍 Python comparison 
# Python's relative import — same idea
from .. import deliver_order

# Each dot = one level up
# .  = current package
# .. = parent package
# ..grandparent = parent's parent

Direct parallel. super:: in Rust is .. in Python. The difference: Rust's super is the only way to go up (there's no absolute equivalent that starts with the parent's name), while Python gives you both relative and absolute paths to the same item.

Key takeaway
super:: goes up one level in the module tree. Use it for tightly coupled parent-child relationships where moving them together is likely.
09

Struct & Enum Visibility

Why the name and the contents have separate privacy rules

Making a struct pub exposes the struct name — but its fields stay private unless you mark each one pub individually:

mod back_of_house {
    pub struct Breakfast {
        pub toast: String,          // public — customer picks the bread
        seasonal_fruit: String,      // private — chef decides the fruit
    }

    impl Breakfast {
        pub fn summer(toast: &str) -> Breakfast {
            Breakfast {
                toast: String::from(toast),
                seasonal_fruit: String::from("peaches"),
            }
        }
    }
}

Because seasonal_fruit is private, the struct must provide a public constructor — otherwise no one outside the module can create a Breakfast. This is a feature: private fields let you enforce invariants (rules about valid data) through constructors and methods, not by trusting callers to set things correctly.

Enums are the opposite: making an enum public makes all its variants public.

mod back_of_house {
    pub enum Appetizer {
        Soup,    // automatically public
        Salad,   // automatically public
    }
}

Why the difference? Structs model data with invariants — rules that must hold, like "a bank account's balance can't go negative." Private fields let you enforce those rules. Enums model choices — the caller needs to know all the options to handle them. Making every variant private would be pointless; you'd just annotate every one with pub anyway.

🐍 Python comparison 
from dataclasses import dataclass

# Python — everything is public, invariants are your problem
@dataclass
class Breakfast:
    toast: str
    seasonal_fruit: str     # anyone can set this directly

# No way to make a field "private" — _seasonal_fruit is just a hint
meal = Breakfast("Rye", "peaches")
meal.seasonal_fruit = "blueberries"  # Python won't stop you

Python's dataclasses have no enforced field privacy. You can use properties to control access, but it's opt-in boilerplate. Rust's per-field pub is built into the language — private fields are truly private, and the compiler forces you to provide a constructor if you need them set from outside.

Key takeaway
pub struct = public name, private fields (annotate individually). pub enum = public name, all variants public. Structs hide fields to protect invariants; enums expose variants so callers can match them.

10

Shortcuts with use

Bringing a path into scope so you don't have to repeat it

Typing crate::front_of_house::hosting::add_to_waitlist() every time you call the function is painful. The use keyword creates a local shortcut — bring a path into scope once, use the shorter name everywhere.

use crate::front_of_house::hosting;

pub fn eat_at_restaurant() {
    hosting::add_to_waitlist();  // much cleaner
}

use is like creating a symbolic link. After the declaration, hosting is a valid name in this scope — just as if the module had been defined here. But it's scoped: move eat_at_restaurant into a child module, and the shortcut disappears. You'd need a new use in that module.

🐍 Python comparison 
# Rust's `use` is Python's `from ... import`
use crate::front_of_house::hosting;          # Rust
from my_project.front_of_house import hosting  # Python

# Then use it locally in both languages
hosting.add_to_waitlist()

The parallel is almost exact. Both create a local name that points to something defined elsewhere. Both are scoped to the file (Python) or the block (Rust). The key difference: Python's import happens at runtime and can fail if the module isn't on sys.path; Rust's use is resolved at compile time — if it compiled, the path is valid.

Key takeaway
use path::to::module; creates a local shortcut. It's scoped to where it's declared — just like a local variable.
11

Idiomatic use Patterns

Functions: import the parent. Structs/enums: import the item.

Rust has two conventions for use, and the distinction is about readability:

What you're importingIdiomatic patternWhy
FunctionsImport the parent moduleMakes it clear the function isn't local
Structs, enums, etc.Import the item itselfThe name is the type — short is fine
// ✅ Functions — import the parent
use crate::front_of_house::hosting;
hosting::add_to_waitlist();     // clearly not a local function

// ✅ Structs — import the item
use std::collections::HashMap;
let mut map = HashMap::new();    // short and clean

// ⚠️ Works, but unclear where add_to_waitlist comes from
use crate::front_of_house::hosting::add_to_waitlist;
add_to_waitlist();               // looks like a local function — misleading
⚠️ Common mistake — importing two things with the same name 
use std::fmt::Result;
use std::io::Result;    // ❌ error[E0255]: the name `Result` is defined multiple times

// Fix option 1: stop at the parent module
use std::fmt;
use std::io;
// Then use fmt::Result and io::Result

// Fix option 2: alias one of them (see next section)
use std::io::Result as IoResult;

In Python, importing two things with the same name just shadows the first one silently. In Rust, it's a compile error — the compiler won't guess which one you meant.

Key takeaway
Functions: use the parent module (hosting::add_to_waitlist()). Structs/enums: use the item (HashMap). This is convention, not enforced — but it makes code easier to read.
12

Aliases with as

Renaming imports when two types have the same name

When you need two types with the same name in scope, as gives one a different local name:

use std::fmt::Result;
use std::io::Result as IoResult;

fn function1() -> Result { /* uses fmt::Result */ }
fn function2() -> IoResult<()> { /* uses io::Result */ }
🐍 Python comparison 
# Python — identical concept
import numpy as np
from typing import Optional as Opt

# Rust
use std::io::Result as IoResult

Same keyword, same purpose. Rust even borrowed the name from Python.

Key takeaway
use path::Type as Alias; renames an import in the current scope. The cleanest fix for name conflicts.
13

Re-exporting with pub use

Reshaping your public API for consumers of your crate

A regular use creates a private shortcut — only the current scope can use it. pub use does two things: it creates the shortcut and makes it publicly available to anyone using your crate.

mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {}
    }
}

// Re-export: makes `hosting` available at the crate root
pub use crate::front_of_house::hosting;

Without pub use, external code must write restaurant::front_of_house::hosting::add_to_waitlist(). With it, they can write restaurant::hosting::add_to_waitlist(). You've flattened the internal structure for consumers without changing how your code is organized.

This is powerful because it lets you decouple your internal structure from your public API. Organize code however makes sense for development, then use pub use to present a clean surface.

🐍 Python comparison 
# Python's equivalent: re-exporting from __init__.py
# __init__.py
from .front_of_house.hosting import add_to_waitlist

# Now users can do:
from restaurant import add_to_waitlist  # flattened!
# Instead of:
from restaurant.front_of_house.hosting import add_to_waitlist

Same concept. Python packages re-export from __init__.py to create a clean API. Rust uses pub use. The difference: Python's re-export is just another import statement that anyone can bypass with a direct import. Rust's pub use is the only way to access it from outside the crate — there's no bypassing the privacy system.

💡 Insight — when to use pub use

Use pub use when your internal module structure reflects the implementation (e.g., separate files for separate concerns) but your users think in terms of the domain (e.g., they just want hosting::add_to_waitlist, not front_of_house::hosting::add_to_waitlist). Libraries on crates.io use this extensively — the internal module tree can be deep and messy, but the public API is flat and clean.

Key takeaway
pub use re-exports an item: brings it into scope and makes it publicly available. Use it to design a clean API that differs from your internal structure.
14

External Packages

crates.io, Cargo.toml, and the standard library

To use code someone else published, add it to Cargo.toml:

[dependencies]
rand = "0.8.5"

Cargo downloads the package and its dependencies from crates.io, compiles them, and makes them available. Then use the items you need:

use rand::Rng;

fn main() {
    let secret = rand::thread_rng().gen_range(1..=100);
}

The standard library (std) is also an external crate — but it ships with Rust, so you don't add it to Cargo.toml. You still need use to bring items from it into scope:

use std::collections::HashMap;
🐍 Python comparison 
# Python: declare in pyproject.toml, install with pip, then import
# pyproject.toml
[project]
dependencies = ["numpy>=1.24"]

# Shell
$ pip install -e .

# Code
import numpy as np

# Rust: declare in Cargo.toml, Cargo downloads + compiles automatically
# Cargo.toml
rand = "0.8.5"

# Code (no separate install step — cargo build does it)
use rand::Rng;

The workflow is the same: declare → install → import. The difference is when it happens. Python installs at setup time and imports at runtime. Rust downloads and compiles at build time — there's no separate install step, and no runtime surprises. If it compiled, the dependency exists.

Also, Rust's std is Python's standard library — both are always available without a Cargo.toml/requirements.txt entry.

Key takeaway
Add external crates to Cargo.toml, then use their items. std is always available without a Cargo entry. Cargo handles download and compilation automatically.
15

Nested Paths & Glob

Cleaning up long import lists, and when to use *

Nested paths

When importing multiple items from the same module, collapse them into one line:

// Before — two lines with a shared prefix
use std::cmp::Ordering;
use std::io;

// After — nested path with curly brackets
use std::{cmp::Ordering, io};

You can nest at any depth. When one path is a subpath of another, use self to import both the module itself and something from inside it:

// Two lines — one is a subpath of the other
use std::io;
use std::io::Write;

// Merged — `self` means "the module itself"
use std::io::{self, Write};

The glob operator

use path::*; imports every public item from a module:

use std::collections::*;   // HashMap, BTreeMap, HashSet, ... everything

Glob is convenient but dangerous in general code — it makes names hard to trace and can cause silent collisions when a dependency upgrades. Two places where it's acceptable:

  • Testing — bringing everything under test into the tests module (Chapter 11).
  • Prelude patterns — some crates provide a prelude module designed to be glob-imported.
🐍 Python comparison 
# Nested paths — Python doesn't have this syntax
# You'd write separate imports:
from os.path import join, exists
import os

# Glob — Python has the exact equivalent
from os.path import *    # same risk as Rust's glob

# Both communities agree: glob is for testing and preludes, not production code.

Python's from module import * is Rust's use module::*; — same risk, same community consensus against it. The difference: Python will silently shadow names; Rust will give you a compile error if two glob imports bring in the same name.

⚠️ Common mistake — glob import causes a name collision after an upgrade 
use some_crate::*;   // imports everything
use another_crate::*; // imports everything

// Works today. But if some_crate v1.2 adds a public `Config` type,
// and another_crate already has one, you get:
// error[E0659]: `Config` is ambiguous
//
// This is why glob imports make upgrades fragile.
Key takeaway
use std::{cmp::Ordering, io}; collapses shared-prefix imports. use path::*; imports everything — reserve it for tests and preludes, not general code.
Chapter 7 Summary
  • A crate is the compiler's unit — one root file, one privacy boundary. Binary crates have main; library crates don't.
  • A package is one Cargo.toml + one library (at most) + binaries (unlimited) + at least one of either.
  • Cargo discovers crates by filename: src/main.rs, src/lib.rs, src/bin/*.rs.
  • mod name; declares a module — the compiler finds it inline, in src/name.rs, or src/name/mod.rs.
  • Everything is private by default. Children can see ancestors; parents can't see into children.
  • Absolute paths start with crate::; relative paths start from the current module. Both use ::.
  • pub mod makes a module visible; pub on the item makes it usable. Both are needed.
  • super:: goes up one level — the Rust equivalent of Python's .. relative import.
  • pub struct = public name, private fields. pub enum = public name, all variants public.
  • Keep the module tree in src/lib.rs; make src/main.rs a thin wrapper.
  • use creates a local shortcut for a path — scoped to where it's declared.
  • Functions: use the parent module. Structs/enums: use the full path.
  • use path as Alias; renames imports to avoid name conflicts.
  • pub use re-exports — decouple internal structure from your public API.
  • Add external crates to Cargo.toml; std is always available without an entry.
  • Nested paths: use std::{cmp::Ordering, io};. Glob: use path::*; — testing and preludes only.
