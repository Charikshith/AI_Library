Part A · Chapter 5.1

Defining and Instantiating Structs

Custom types that group related, named pieces of data together

01

What Is a Struct

Why group related data into one type

So far your data has been single values — an i32, a String. But real programs deal with things made of several values: a user has a name, an email, and a login count. A rectangle has a width and a height. Passing those around as loose separate variables is error-prone.

A struct (short for "structure") lets you name a bundle of values and treat it as one custom type. Each piece of data gets a name, called a field. Because you name the fields, a struct is more flexible than a tuple — you don't rely on position.

If you know Python's classes or @dataclass, you already have the mental model. The big difference: a struct holds only data. Behavior lives in a separate impl block (Part C), and ownership rules from Chapter 4 apply to every field.

🐍 The Python parallel 
from dataclasses import dataclass

@dataclass
class User:
    active: bool
    username: str
    email: str
    sign_in_count: int

A Rust struct is almost exactly a @dataclass: named fields, each with a type. The difference is that a struct never contains methods in its definition — those go in a separate impl block — and every field is owned according to Chapter 4's rules.

Key takeaway
A struct is a custom type that bundles several named fields into one meaningful package — like a Python dataclass, but with data and behavior kept separate.
02

Defining and Instantiating

Declaring fields, then filling them in

You define a struct with the struct keyword and a name, then list each field with its type. Defining it doesn't create any data — it's a blueprint. To actually use it, you create an instance by giving a concrete value for every field.

// Definition — a blueprint. No data exists yet.
struct User {
    active: bool,
    username: String,
    email: String,
    sign_in_count: u64,
}

fn main() {
    // Instance — one concrete User. Order of fields doesn't matter.
    let user1 = User {
        active: true,
        username: String::from("someusername123"),
        email: String::from("someone@example.com"),
        sign_in_count: 1,
    };
}

To read a value, use dot notation: user1.email. Because you name each field explicitly at creation, you can list them in any order — unlike a tuple, where position is everything.

🐍 Python comparison 
user1 = User(
    active=True,
    username="someusername123",
    email="someone@example.com",
    sign_in_count=1,
)
print(user1.email)   # same dot access

The instantiation reads like Python's keyword arguments, and field access is identical. The key difference is that Rust checks at compile time that you supplied every field with the right type — no missing or misspelled attributes slip through.

⚠️ Common mistake — forgetting a field 
let user1 = User {
    active: true,
    username: String::from("someusername123"),
    email: String::from("someone@example.com"),
    // sign_in_count is missing!
};   // ❌ error[E0063]: missing field `sign_in_count` in initializer of `User`

Rust requires every field to have a value. The compiler caught a bug that Python would only surface later, when something tried to read the missing attribute.

Key takeaway
struct declares the blueprint; a User { ... } literal creates an instance with a value for every field, in any order.
03

Accessing and Mutating Fields

Dot notation and the whole-instance mut rule

You read and write fields with the same dot notation. But to change a field, the entire instance must be mutable — you cannot mark just one field as mutable. This is a deliberate rule: mutability in Rust is a property of the binding, not of individual fields.

fn main() {
    let mut user1 = User {          // the whole instance is mutable
        active: true,
        username: String::from("someusername123"),
        email: String::from("someone@example.com"),
        sign_in_count: 1,
    };

    user1.email = String::from("another@example.com");   // ✅ allowed
}
⚠️ Common mistake — mutating an immutable instance 
let user1 = User { /* ... */ };   // no `mut`
user1.email = String::from("x@y.com");
// ❌ error[E0594]: cannot assign to `user1.email`, as `user1` is not declared as mutable

There's no way to make a single field mutable while the rest stays fixed — it's all-or-nothing per binding. This keeps Rust's mutation rules simple and predictable.

🐍 Python comparison

In Python, every attribute of every object is mutable by default — user1.email = "..." always works. Rust flips the default: values are immutable unless you opt in with mut, and that choice applies to the whole instance.

Key takeaway
Access fields with a dot. To change any field, the whole instance must be declared mut — Rust has no per-field mutability.
04

Field Init Shorthand

Skip the repetition when variable names match field names

It's common to build a struct inside a function whose parameters share the field names. Writing email: email feels redundant. Rust's field init shorthand lets you write just email when the variable and the field have the same name.

fn build_user(email: String, username: String) -> User {
    User {
        active: true,
        username,           // shorthand for `username: username`
        email,              // shorthand for `email: email`
        sign_in_count: 1,
    }
}

This is purely a convenience — it compiles to exactly the same thing as the long form. Reach for it only when the names genuinely match.

🐍 Python comparison

Python has no direct equivalent — you'd still write User(email=email, username=username). The closest cousin is f-string's f"{email=}" debug syntax, but that's for printing, not construction. Rust's shorthand is a small ergonomics win with no runtime difference.

Key takeaway
When a variable's name matches a field's name, write the name once — username instead of username: username.
05

Struct Update Syntax

Build a new instance mostly from an old one

Often you want a new instance that's identical to an existing one except for a field or two. The struct update syntax .. fills in the remaining fields from another instance, so you only spell out what changes.

let user2 = User {
    email: String::from("another@example.com"),
    ..user1     // take every other field from user1
};

The ..user1 must come last. But there's a catch tied straight to Chapter 4: this syntax moves data. Because user1.username is a String (heap-owned), it moves into user2 — so user1 as a whole can no longer be used.

What ..user1 moves
user1                                user2
┌──────────────────┐                 ┌──────────────────┐
│ active: true     │ ── Copy ──────► │ active: true     │
│ username: "..."  │ ── MOVE ──────► │ username: "..."  │   ← String moved
│ email: "old"     │   (replaced)    │ email: "another" │   ← brand new
│ sign_in_count: 1 │ ── Copy ──────► │ sign_in_count: 1 │
└──────────────────┘                 └──────────────────┘

user1.username was moved → user1 is no longer usable as a whole.
⚠️ Common mistake — using user1 after an update-move 
let user2 = User { email: String::from("a@b.com"), ..user1 };
println!("{}", user1.username);
// ❌ error[E0382]: borrow of moved value: `user1.username`

Had you overridden both String fields with new values, only the Copy fields (active, sign_in_count) would be taken from user1 — and user1 would remain fully valid. Move rules from Chapter 4 apply field by field.

🐍 Python comparison 
import dataclasses
user2 = dataclasses.replace(user1, email="another@example.com")

dataclasses.replace is the spiritual twin of struct update syntax. The difference: Python copies references and leaves user1 fully usable, while Rust moves heap-owned fields, invalidating user1.

Key takeaway
..other fills the unspecified fields from another instance — but it moves heap-owned fields, so the source may become unusable.
06

Tuple Structs

Named types without named fields

Sometimes you want the meaning of a named type but the fields don't need names — the position says it all. A tuple struct gives you that: a name for the type, with fields identified by index.

struct Color(i32, i32, i32);   // RGB
struct Point(i32, i32, i32);   // x, y, z

fn main() {
    let black = Color(0, 0, 0);
    let origin = Point(0, 0, 0);

    println!("red channel: {}", black.0);   // access by index, not name
}

Crucially, Color and Point are different types even though both hold three i32s. A function that wants a Point will reject a Color. This lets you give distinct meaning to structurally identical data.

💡 Analogy — same shape, different label

Think of two identical glass jars — one labeled "salt," the other "sugar." Physically interchangeable, but the labels stop you from grabbing the wrong one. Tuple structs are those labels for the compiler: it refuses to swap a Color for a Point even though the bytes match.

🐍 Python comparison

The closest thing is collections.namedtuple or typing.NamedTuple — but Python won't stop you from passing a Color where a Point is expected, since it's all just tuples at runtime. Rust makes them genuinely incompatible types.

Key takeaway
A tuple struct names a type but numbers its fields (.0, .1). Two tuple structs with identical fields are still distinct, incompatible types.
07

Unit-Like Structs

Structs with no data at all

You can define a struct with no fields. These are called unit-like structs because they behave like (), the unit type. Why would you want a type that stores nothing? Because sometimes you need a type to hang behavior on — to implement a trait — without any data to go with it.

struct AlwaysEqual;

fn main() {
    let subject = AlwaysEqual;   // no parentheses, no braces
}

Later, in Chapter 10, you'll implement traits (shared behavior) on types. A unit-like struct is perfect when the behavior matters but there's genuinely no state to carry — for example, a marker type or a trait implementation that always returns the same result.

Don't over-teach yourself here. Unit-like structs only become useful once you've met traits. For now, just know they exist and that a struct can hold zero fields.
Key takeaway
A unit-like struct (struct AlwaysEqual;) has no fields — useful purely as something to attach behavior to.
08

Ownership of Struct Data

Why fields use owned String, not &str

You may have wondered why the User struct used String (owned) rather than &str (a borrowed slice from Chapter 4). The reason ties directly to ownership: a struct should own all of its data, so that data stays valid for as long as the whole struct is valid.

If a field were a reference, that reference would point to data owned by something else. Then you'd have to guarantee the borrowed data outlives the struct — and expressing that guarantee requires lifetimes, which the compiler will demand you spell out.

struct User {
    username: &str,     // a reference — borrows data owned elsewhere
    email: &str,
}
// ❌ error[E0106]: missing lifetime specifier
// help: consider introducing a named lifetime parameter: `<'a>`

The compiler isn't being difficult — it caught a real ambiguity. It has no way to know how long that borrowed string will live. Using owned String sidesteps the whole question: the struct owns its data, full stop.

We'll return to this. Storing references in structs is entirely possible, but it needs lifetime annotations — a Chapter 10 topic. For now, prefer owned types like String in your struct fields.
🐍 Python comparison

Python never makes you think about this — every attribute is just a reference to a heap object, and the garbage collector keeps things alive as long as anything points to them. Rust has no GC, so it must know at compile time who owns what. Owning the data is the simplest, safest default.

Key takeaway
Give struct fields owned types like String so the struct owns its data — storing references would require lifetimes, saved for later.

09

Refactoring With Structs

From loose variables to a type that means something

Let's compute the area of a rectangle and watch why a struct is the right tool. First, the naive version — two unrelated parameters:

// v1 — width and height are separate. Nothing ties them together.
fn area(width: u32, height: u32) -> u32 {
    width * height
}

The signature area(width, height) doesn't say these two numbers belong to one rectangle. A tuple groups them, but then .0 and .1 lose all meaning. A struct gives us the best of both — grouped and named:

struct Rectangle {
    width: u32,
    height: u32,
}

// v3 — one parameter that clearly means "a rectangle".
// We borrow with & so main keeps ownership (Chapter 4!).
fn area(rectangle: &Rectangle) -> u32 {
    rectangle.width * rectangle.height
}

fn main() {
    let rect = Rectangle { width: 30, height: 50 };
    println!("Area: {}", area(&rect));   // 1500 — rect still usable after
}

Notice &Rectangle: area only needs to read the rectangle, so it borrows an immutable reference. main keeps ownership and can keep using rect. This is Chapter 4's borrowing put to work on your own type.

Key takeaway
A struct turns related loose variables into one named, meaningful type — and functions borrow it with & to read without taking ownership.
10

Deriving Debug

Teaching Rust how to print your struct

Try to print a Rectangle the obvious way and Rust stops you:

println!("rect is {rect}");
// ❌ error[E0277]: `Rectangle` doesn't implement `std::fmt::Display`

The {} placeholder uses Display, which is meant for end-user output — and Rust can't guess how your struct should look to a user. For developer-facing inspection there's {:?}, which uses the Debug trait. But your struct has to opt in first with a #[derive(Debug)] annotation:

#[derive(Debug)]          // auto-generate a Debug implementation
struct Rectangle {
    width: u32,
    height: u32,
}

fn main() {
    let rect = Rectangle { width: 30, height: 50 };

    println!("rect is {rect:?}");    // Rectangle { width: 30, height: 50 }
    println!("rect is {rect:#?}");   // pretty-printed over multiple lines
}

The {:#?} variant pretty-prints across lines — handy for larger structs. derive is Rust asking the compiler to write boilerplate for you; you'll see it again for traits like Clone and PartialEq.

🐍 Python comparison 
@dataclass
class Rectangle:
    width: int
    height: int

print(rect)   # Rectangle(width=30, height=50) — __repr__ is free

A Python @dataclass gives you a readable __repr__ automatically. Rust makes it explicit: nothing is printable until you opt in with #[derive(Debug)]. Slightly more typing, but zero surprises about what's printable.

Key takeaway
Add #[derive(Debug)] to make a struct printable with {:?} (compact) or {:#?} (pretty) — Rust never prints your types until you opt in.
11

The dbg! Macro

Inspecting values without breaking the flow

Beyond println!, Rust ships a dbg! macro built for quick debugging. It prints the file and line number, the expression, and its value — then hands the value back, so you can wrap it around an expression without disrupting your code.

#[derive(Debug)]
struct Rectangle { width: u32, height: u32 }

fn main() {
    let scale = 2;
    let rect = Rectangle {
        width: dbg!(30 * scale),   // prints "30 * scale = 60", returns 60
        height: 50,
    };

    dbg!(&rect);   // borrow so dbg! doesn't take ownership of rect
}

Two things to notice. First, dbg! prints to stderr (not stdout like println!), so it won't pollute your program's real output. Second, it takes ownership of what you pass and returns it — so we pass &rect to borrow instead, keeping rect usable afterward.

Rule of thumb: use println!("{x:?}") for logging you want to keep, and dbg! for temporary "what is this value right now?" checks you'll delete later.
Key takeaway
dbg!(&value) prints the file, line, expression, and value to stderr and returns the value — a purpose-built debugging tool that println! can't quite match.

12

Defining Methods

Attaching behavior with an impl block

So far area was a free-standing function. But area is really behavior of a rectangle — it belongs with the type. A method is a function defined inside an impl (implementation) block for a struct, whose first parameter is always self.

#[derive(Debug)]
struct Rectangle { width: u32, height: u32 }

impl Rectangle {                // everything about Rectangle's behavior
    fn area(&self) -> u32 {     // &self = borrow the instance we're called on
        self.width * self.height
    }
}

fn main() {
    let rect = Rectangle { width: 30, height: 50 };
    println!("Area: {}", rect.area());   // call with a dot — no argument needed
}

Now you call it as rect.area(). The self refers to the instance the method was called on — here, rect. Grouping the definition and its methods in one impl block keeps everything about Rectangle in one place.

💡 Insight — automatic referencing

In some languages you'd write (&rect).area() when a method takes &self. Rust does automatic referencing: given rect.area(), it automatically adds &, &mut, or * to match the method's self. So the same rect.method() syntax works no matter how the method borrows.

🐍 Python comparison 
class Rectangle:
    def area(self):
        return self.width * self.height

Nearly identical — both use an explicit self first parameter and call with a dot. The difference is location: Python puts methods inside the class body, Rust puts them in a separate impl block. And Rust's self can borrow (&self) or own (self), which Python never distinguishes.

Key takeaway
Methods live in an impl block, take self as their first parameter, and are called with a dot: rect.area().
13

self, &self, and &mut self

How a method borrows — or takes — its instance

The form of self decides what the method may do with the instance. It's Chapter 4's ownership rules applied to methods, and choosing the right one is most of the skill:

The three forms of self
  1. &self — borrow immutably. Read the fields; can't change them. The default and most common.
  2. &mut self — borrow mutably. Read and modify fields. Requires the caller's binding to be mut.
  3. self — take ownership. The instance is moved into the method and consumed. Rare — used when transforming a value into something else.
impl Rectangle {
    fn area(&self) -> u32 {          // reads only
        self.width * self.height
    }

    fn double_width(&mut self) {      // mutates a field
        self.width *= 2;
    }
}

fn main() {
    let mut rect = Rectangle { width: 30, height: 50 };
    rect.double_width();               // needs `mut` on rect
    println!("{}", rect.area());       // 3000
}
⚠️ Common mistake — mutating through &self 
impl Rectangle {
    fn grow(&self) {        // only borrowed immutably...
        self.width += 1;      // ...but tries to change a field
    }
}
// ❌ error[E0594]: cannot assign to `self.width`, which is behind a `&` reference

To modify, the method must take &mut self, and the instance must be declared mut. The compiler enforces the same "one mutable borrow" discipline you learned in Chapter 4.

Key takeaway
Use &self to read, &mut self to modify, and bare self (rarely) to consume the instance — the same borrow rules as Chapter 4.
14

Methods vs Fields

Same name, different meaning

A method can share its name with a field. Rust tells them apart by the parentheses: rect.width reads the field, while rect.width() calls the method. This is often used to build getters — methods that return a field's value.

impl Rectangle {
    fn width(&self) -> bool {
        self.width > 0          // the method: "does it have a width?"
    }
}

fn main() {
    let rect = Rectangle { width: 30, height: 50 };

    if rect.width() {                 // method call — returns bool
        println!("width is {}", rect.width);   // field access — returns u32
    }
}

Why bother? Getters matter once you make fields private (Chapter 7): outside code can call width() to read the value but can't assign to the field directly. It's the read-only-access pattern, enforced by the compiler.

🐍 Python comparison 
class Rectangle:
    @property
    def width(self):
        return self._width

Python's @property lets an attribute access secretly run a method — no parentheses at the call site. Rust keeps them visually distinct: () always means "call a method." Less magic, more clarity about what's happening.

Key takeaway
rect.width reads a field; rect.width() calls a method — the parentheses disambiguate, enabling read-only getters over private fields.
15

Methods With More Parameters

Passing another struct in

Methods can take parameters beyond self. A classic example: does one rectangle fully fit inside another? The method borrows self and a reference to the other rectangle.

impl Rectangle {
    fn can_hold(&self, other: &Rectangle) -> bool {
        self.width > other.width && self.height > other.height
    }
}

fn main() {
    let rect1 = Rectangle { width: 30, height: 50 };
    let rect2 = Rectangle { width: 10, height: 40 };

    println!("Can rect1 hold rect2? {}", rect1.can_hold(&rect2));   // true
}

Note the second parameter is &Rectangle, not Rectangle — we only need to read other, so we borrow it. After the call, both rect1 and rect2 remain usable. Every method parameter follows the same ownership choices as any function.

Key takeaway
Methods can take extra parameters after self — and you borrow them with & when you only need to read, keeping the caller's values intact.
16

Associated Functions

Functions in impl that don't take self

Not every function in an impl block needs an instance. A function without a self parameter is an associated function — it's tied to the type but doesn't operate on a specific instance. You've already used one: String::from. These are commonly used as constructors.

impl Rectangle {
    // No self — this builds a Rectangle rather than using one.
    fn square(size: u32) -> Self {
        Self { width: size, height: size }   // Self = Rectangle
    }
}

fn main() {
    let sq = Rectangle::square(3);   // call with :: not . — Rectangle { 3, 3 }
}

Two things to spot. You call an associated function with the :: syntax on the type — Rectangle::square(3) — not with a dot on an instance. And Self (capital S) is a handy alias for the type the impl block is for, so you don't have to repeat Rectangle.

🐍 Python comparison 
class Rectangle:
    @classmethod
    def square(cls, size):
        return cls(size, size)

sq = Rectangle.square(3)

An associated function is Rust's version of a @classmethod or @staticmethod — a factory that lives on the type, not an instance. The :: call syntax even mirrors Python's ClassName.method(). Rust's Self plays the role of cls.

Key takeaway
An associated function has no self, is called with Type::name(), and often serves as a constructor — like String::from and Rectangle::square.
17

Multiple impl Blocks

Organizing behavior however suits you

A struct can have any number of impl blocks. Splitting methods across several blocks is perfectly valid Rust — each block just adds more behavior to the same type.

impl Rectangle {
    fn area(&self) -> u32 {
        self.width * self.height
    }
}

impl Rectangle {                      // a second block — totally fine
    fn can_hold(&self, other: &Rectangle) -> bool {
        self.width > other.width && self.height > other.height
    }
}

For a simple type there's no reason to split like this. But it becomes genuinely useful with generic types and traits (Chapter 10), where different impl blocks apply under different conditions. For now, just know the option exists.

Key takeaway
A type may have multiple impl blocks — harmless for simple structs, and essential once generics and traits arrive.
