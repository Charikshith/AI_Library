Enums and Pattern Matching

A struct says a value has all of these fields. An enum says a value is one of these variants — and each variant can carry its own data. Paired with match, enums let you model choices exactly and force yourself to handle every case. This is where Rust starts to feel special.

Part A · Chapter 6.1

Defining an Enum

Types whose values are one of a fixed, named set of possibilities

01

What Is an Enum

Modeling "one of a fixed set of possibilities"

A struct groups data that always appears together — a rectangle always has a width and a height. But some data is an either-or. An IP address is version four or version six, never both. A coin is a penny, nickel, dime, or quarter. That's an enumeration, or enum: a type whose value is exactly one of a fixed set of named variants.

Enums exist in many languages, but Rust's are unusually powerful: each variant can carry its own data. That turns an enum into a precise model of a decision — and the compiler guarantees you handle every branch.

🐍 The Python parallel 
from enum import Enum

class IpAddrKind(Enum):
    V4 = 1
    V6 = 2

Python's Enum is the closest thing, and it covers the simplest Rust enums. But Python enum members can't each hold different structured data the way Rust variants can — for that you'd reach for a tagged union or a class hierarchy. Rust folds all of that into one enum.

Key takeaway
An enum is a type whose value is exactly one of a fixed set of named variants — and in Rust, each variant can carry its own data.
02

Defining and Using an Enum

Variants and the :: namespacing syntax

Define an enum with the enum keyword and list the variants. Each variant lives in the enum's namespace, so you refer to it with EnumName::Variant.

enum IpAddrKind {
    V4,
    V6,
}

fn main() {
    // Both values have the same type: IpAddrKind
    let four = IpAddrKind::V4;
    let six = IpAddrKind::V6;

    route(four);
    route(six);
}

// Takes any IpAddrKind — a function can accept the enum type
fn route(ip_kind: IpAddrKind) {}

Both four and six have the type IpAddrKind, so a single function can accept either. That's the point: the enum is one type with a fixed set of possible values.

Key takeaway
Declare variants with enum, then name them with EnumName::Variant — every variant shares the enum's type.
03

Variants That Hold Data

Attaching values directly to each variant

Knowing an address is V4 or V6 isn't enough — you need the actual address. You could pair the enum with a struct, but Rust lets you attach data straight to the variant, which is more concise:

enum IpAddr {
    V4(String),      // each V4 carries a String
    V6(String),
}

fn main() {
    // The variant name becomes a constructor function
    let home = IpAddr::V4(String::from("127.0.0.1"));
    let loopback = IpAddr::V6(String::from("::1"));
}

Notice something elegant: IpAddr::V4() is automatically a function that takes a String and returns an IpAddr. Defining the enum gives you these constructors for free.

💡 Insight — variants are constructor functions

When you write V4(String), Rust generates a function IpAddr::V4 with the signature fn(String) -> IpAddr. This becomes genuinely useful later — you can pass IpAddr::V4 anywhere a function is expected, like mapping it over a list of strings. For now, just enjoy that construction is free.

Key takeaway
A variant can hold data — V4(String) — and the variant name doubles as a constructor function returning the enum.
04

Different Data Per Variant

Each variant can carry a totally different shape of data

Here's the real power: variants don't have to hold the same kind of data. One can hold nothing, another a struct-like set of named fields, another a single value, another a tuple. This one enum replaces four different struct definitions:

enum Message {
    Quit,                          // no data at all
    Move { x: i32, y: i32 },        // named fields, like a struct
    Write(String),                 // a single String
    ChangeColor(i32, i32, i32),  // three values, like a tuple
}

fn main() {
    let m1 = Message::Write(String::from("hello"));
    let m2 = Message::Move { x: 10, y: 30 };
    let m3 = Message::ChangeColor(255, 0, 0);
    let m4 = Message::Quit;
}

The advantage over four separate structs is that all four are the same type — Message — so a function can accept any of them, and you handle all the cases in one place (that's what match in Part B is for).

🐍 Python comparison

To model this in Python you'd typically build a class hierarchy — a base Message with Quit, Move, Write, ChangeColor subclasses — or use a tagged union with typing.Union. Rust captures the whole idea in one enum, and crucially, the compiler knows the complete list of variants, which it uses to check your match statements later.

Key takeaway
Each variant can carry a different shape of data — none, named fields, a value, or a tuple — all unified under one enum type.
05

Methods on Enums

"Enums get methods just like structs" is true — but the interesting part is what you do with self inside the method

The mechanic is exactly what you saw in Chapter 5: an impl block attaches functions to a type, and impl doesn't care whether that type is a struct or an enum. You get the same three receiver forms — &self, &mut self, self — and the same associated functions (the enum equivalent of String::from). So the boring answer to "can enums have methods?" is: yes, identically.

enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    ChangeColor(i32, i32, i32),
}

impl Message {
    fn call(&self) { /* ... */ }
}

fn main() {
    let m = Message::Write(String::from("hello"));
    m.call();   // same dot-call syntax as struct methods
}

Now the part that summary glosses over. On a struct, self has one fixed shape — every field is guaranteed to exist, so a method just reaches for them:

struct Point { x: i32, y: i32 }

impl Point {
    fn sum(&self) -> i32 {
        self.x + self.y   // x and y ALWAYS exist — no branching needed
    }
}

On an enum, self could be any of the variants, each with a different shape of data. You can't reach for self.x, because the value in front of you might be a Quit that has no fields at all. So an enum method almost always opens the same way — by matching on self to find out which variant it actually is:

impl Message {
    fn call(&self) {
        match self {
            Message::Quit => {
                println!("Quit — no data");
            }
            Message::Move { x, y } => {
                println!("Move to ({x}, {y})");
            }
            Message::Write(text) => {
                println!("Write: {text}");
            }
            Message::ChangeColor(r, g, b) => {
                println!("Color: {r} {g} {b}");
            }
        }
    }
}

That match self { ... } pattern is the heart of nearly every enum method. Don't worry about the full mechanics of match yet — that's all of Part B — but notice the shape: one method, one match, one arm per variant, each arm handling that variant's specific data.

Struct method vs. enum method — the essential difference
STRUCT  self ─► { x, y }                one fixed shape → just read the fields
                └──────────┐
                           ▼  self.x + self.y

ENUM    self ─► which one? ─┬─ Quit               ─► handle (no data)
                           ├─ Move { x, y }       ─► handle x, y
                           ├─ Write(text)         ─► handle text
                           └─ ChangeColor(r,g,b)  ─► handle r, g, b
                              ▲
                    `match self` picks the right arm at runtime

Why &self and not plain self? The same rule as structs: &self reads the value and the caller keeps ownership afterwards — that's the default you want almost always. &mut self lets the method mutate the enum in place. Plain self consumes the value (rarer — used when the method transforms it into something else). One subtlety: because call takes &self, the bindings the match pulls out — text, x, y — are references borrowed out of the variant, not moves. The original Message stays intact.

Here's a more realistic example where the payoff is obvious — computing the area of different shapes. Each variant carries the numbers that shape needs, and one method gives variant-specific behavior behind a single dot-call:

enum Shape {
    Circle(f64),           // radius
    Rectangle(f64, f64),   // width, height
    Triangle(f64, f64),    // base, height
}

impl Shape {
    fn area(&self) -> f64 {
        match self {
            Shape::Circle(r)       => std::f64::consts::PI * r * r,
            Shape::Rectangle(w, h) => w * h,
            Shape::Triangle(b, h)  => 0.5 * b * h,
        }
    }
}

fn main() {
    let shapes = [
        Shape::Circle(2.0),
        Shape::Rectangle(3.0, 4.0),
        Shape::Triangle(6.0, 8.0),
    ];
    for s in &shapes {
        println!("area = {:.2}", s.area());
    }
}

Three shapes, three formulas, one operation — unified behind s.area(). The loop doesn't know or care which variant each s is; the method sorts that out internally.

💡 Insight — why bundling this into impl is such a good design

Three reasons this pays off:

  1. The operation lives next to the type. Everything about a Shape — its variants and what "area" means for each — sits in one place, not scattered across free functions.
  2. Callers use s.area(), not area(&s). The behavior reads as something the value does, and it's discoverable through the dot.
  3. The compiler becomes your checklist. Add a new variant — say Shape::Square(f64) — and every method whose match doesn't handle it fails to compile, pointing you at the exact spot. The compiler turns "I added a variant" into "here are the exact methods you need to update." (You'll see this exhaustiveness check up close in §10.)
🐍 Python comparison 
class Shape:
    def area(self) -> float:
        match self:
            case Circle(r):       return math.pi * r * r
            case Rectangle(w, h): return w * h
            case Triangle(b, h):  return 0.5 * b * h

The Python instinct is a class hierarchy with area() overridden per subclass — polymorphism spreads the logic across classes. Rust's enum keeps it in one method with one match. The real difference isn't syntax: if you forget a case in Python, it silently returns None and you find out at runtime. Rust refuses to compile until every variant is handled.

⚠️ Common mistake — reaching for fields like it's a struct 
impl Message {
    fn call(&self) {
        println!("{} {}", self.x, self.y);
    }
}
// ❌ error[E0609]: no field `x` on type `&Message`

self here is a Message, which might be Quit (no fields) or Write(String) (a value, no x). There is no single self.x to reach for — the fields only exist inside a specific variant. You have to match self first to get into the arm where x and y are in scope.

Key takeaway
A struct method answers "given these fields, do X." An enum method answers "given which of several shapes I am, do the right X for that shape." The impl machinery is identical — the enum method just almost always opens with match self.
06

The Option Enum

Rust's principled replacement for null

Here's one of Rust's best ideas. Many languages have null — a value meaning "nothing here." The trouble is you can accidentally use a null as if it were real, causing crashes (Tony Hoare, who invented it, calls it his "billion-dollar mistake"). Rust has no null. Instead, the standard library defines an enum:

enum Option<T> {   // T is a generic — works for any type
    None,             // there is no value
    Some(T),          // there is a value, and here it is
}

Option<T> is so useful it's in scope everywhere — you write Some and None without any prefix. The <T> means it works for any type: Option<i32>, Option<String>, and so on.

let some_number = Some(5);              // inferred Option<i32>
let some_char = Some('e');             // inferred Option<char>
let absent: Option<i32> = None;      // must annotate — None alone gives no type

Why is this better than null? Because Option<i32> and i32 are different types. You can't accidentally use a maybe-missing value as if it were definitely there — the compiler forces you to check for None first.

⚠️ Common mistake — using Option as if it were the value 
let x: i8 = 5;
let y: Option<i8> = Some(5);
let sum = x + y;
// ❌ error[E0277]: cannot add `Option<i8>` to `i8`

You can't add an Option<i8> to an i8 — they're different types. To get at the value, you must first handle the possibility that it's None (with match, coming up next). This is exactly the safety net that null lacks.

🐍 Python comparison 
value: Optional[int] = get_value()
# Nothing STOPS you from doing this:
result = value + 1   # 💥 TypeError at runtime if value is None

Python's None and Optional[int] are advisory — type checkers may warn, but Python will happily run None + 1 and crash. Rust makes it a hard compile error: you literally cannot reach the inner value without handling None. The mistake becomes impossible, not just discouraged.

Key takeaway
Rust has no null; Option<T> is either Some(value) or None, and the compiler forces you to handle the None case before using the value.
Part B · Chapter 6.2

The match Control Flow Construct

Compare a value against patterns and run code for whichever matches — exhaustively

07

Matching With match

A switch statement, but far more capable

match compares a value against a series of patterns and runs the code for the first one that fits. Think of it as a coin-sorting machine: the coin falls through until it hits the first hole it fits, and that determines what happens.

enum Coin {
    Penny,
    Nickel,
    Dime,
    Quarter,
}

fn value_in_cents(coin: Coin) -> u8 {
    match coin {
        Coin::Penny   => 1,     // each arm: PATTERN => CODE
        Coin::Nickel  => 5,
        Coin::Dime    => 10,
        Coin::Quarter => 25,
    }
}

Each arm is a pattern, then =>, then the code to run. match is an expression — it produces a value, so here the whole match becomes the function's return value. If an arm needs multiple lines, wrap them in { }.

🐍 Python comparison 
match coin:
    case Coin.PENNY:   value = 1
    case Coin.NICKEL:  value = 5
    case Coin.DIME:    value = 10
    case Coin.QUARTER: value = 25

Python 3.10+ added structural pattern matching with match/case, which looks similar. The two big differences: Rust's match is an expression that returns a value, and Rust requires you cover every case — Python's match silently does nothing if no case fits.

Key takeaway
match runs the code of the first pattern a value fits, and it's an expression — the matching arm's value becomes the result.
08

Patterns That Bind to Values

Pulling the data out of a variant

When a variant holds data, a match arm can bind that data to a name so you can use it. Say quarters now carry which US state they came from:

#[derive(Debug)]
enum UsState {
    Alabama,
    Alaska,
    // ... etc
}

enum Coin {
    Penny,
    Nickel,
    Dime,
    Quarter(UsState),   // this variant carries a state
}

fn value_in_cents(coin: Coin) -> u8 {
    match coin {
        Coin::Penny   => 1,
        Coin::Nickel  => 5,
        Coin::Dime    => 10,
        Coin::Quarter(state) => {   // bind the inner value to `state`
            println!("State quarter from {state:?}!");
            25
        }
    }
}

When a Coin::Quarter(UsState::Alaska) matches, state binds to UsState::Alaska, and you can use it inside the arm. This is how you reach the data a variant carries — match destructures it for you.

How binding works
value:  Coin::Quarter(UsState::Alaska)
                      │
pattern: Coin::Quarter(state)
                       │
                       └──► state = UsState::Alaska   ← usable in the arm body
Key takeaway
A pattern like Coin::Quarter(state) binds the variant's inner data to state, letting you use it inside that arm.
09

Matching Option<T>

Safely handling "maybe a value"

Now the payoff for Option<T>. Because it's just an enum, you handle it with match — and the compiler makes sure you deal with None. Here's a function that adds one to a number that might be absent:

fn plus_one(x: Option<i32>) -> Option<i32> {
    match x {
        None => None,                // no value in → no value out
        Some(i) => Some(i + 1),      // bind the value to i, add 1, re-wrap
    }
}

fn main() {
    let five = Some(5);
    let six = plus_one(five);    // Some(6)
    let none = plus_one(None);    // None
}

The Some(i) arm binds the inner value so you can work with it; the None arm handles absence explicitly. There's no way to forget the None case — as the next section shows, the compiler won't let you.

Key takeaway
Handle an Option<T> by matching its Some(value) and None arms — the Some arm binds the inner value for you to use.
10

Matches Are Exhaustive

The compiler makes you cover every case

This is the safety guarantee that makes match so trustworthy: it must be exhaustive. You have to handle every possible variant. Leave one out and the code won't compile.

fn plus_one(x: Option<i32>) -> Option<i32> {
    match x {
        Some(i) => Some(i + 1),
        // forgot the None arm!
    }
}
// ❌ error[E0004]: non-exhaustive patterns: `None` not covered

The compiler knows every variant of the enum, so it knows exactly what you missed — and it says so by name. This eliminates a whole category of bugs: the "I forgot to handle that case" crash simply cannot ship.

💡 Insight — why this matters so much

In most languages, forgetting a case in a switch is a silent bug you discover in production. In Rust it's a compile error. Better still, when you later add a new variant to an enum, every match that doesn't handle it stops compiling — the compiler hands you a to-do list of every place you need to update. Exhaustiveness turns the compiler into a refactoring assistant.

Key takeaway
A match must handle every possible variant — leave one out and you get a compile error naming exactly what you missed.
11

Catch-all Patterns and _

Handling "everything else" without listing it all

Exhaustiveness sounds heavy when an enum has many variants but you only care about a few. Two catch-all patterns solve this. A named binding catches every remaining value and gives you access to it:

let dice_roll = 9;
match dice_roll {
    3 => add_fancy_hat(),
    7 => remove_fancy_hat(),
    other => move_player(other),   // catches all other rolls, binds to `other`
}

If you don't need the value, use _ — the wildcard that matches anything and binds nothing:

match dice_roll {
    3 => add_fancy_hat(),
    7 => remove_fancy_hat(),
    _ => reroll(),          // "anything else" — value ignored
}

// And to explicitly do nothing for the rest, use the unit value ():
match dice_roll {
    3 => add_fancy_hat(),
    7 => remove_fancy_hat(),
    _ => (),               // nothing happens for any other roll
}

The catch-all must come last — arms are tried top to bottom, so anything after a catch-all would be unreachable. Use other when you need the value, _ when you don't.

⚠️ Common mistake — catch-all not last 
match dice_roll {
    _ => reroll(),        // catch-all first...
    3 => add_fancy_hat(),   // ...makes this unreachable
}
// ❌ warning: unreachable pattern — the `_` above already matched everything

Since arms are evaluated in order, a catch-all placed early swallows every value before the specific arms get a chance. Always put _ or a named catch-all at the bottom.

Key takeaway
Cover the remaining cases with a named binding (other) when you need the value, or _ when you don't — and always place it last.
Part C · Chapter 6.3

Concise Control Flow with if let

A lighter syntax for when you care about one pattern and want to ignore the rest

12

if let

A shorthand when only one pattern matters

Sometimes a full match is overkill. If you only want to act on one pattern and ignore everything else, the _ => () arm is just noise. Look at this match that only cares about Some:

let config_max = Some(3u8);
match config_max {
    Some(max) => println!("The maximum is configured to be {max}"),
    _ => (),   // we don't care about None — but must write this arm
}

if let expresses the same thing more concisely. It runs its block only when the value matches the pattern, binding any inner data:

let config_max = Some(3u8);
if let Some(max) = config_max {
    println!("The maximum is configured to be {max}");
}
// Reads as: "if config_max matches Some(max), run this with max bound"

It's exactly the same behavior — less to type, easier to read. The tradeoff: you give up the exhaustiveness check, since you're deliberately handling only one case. Use it when that's genuinely what you want.

🐍 Python comparison 
if config_max is not None:
    max = config_max
    print(f"The maximum is configured to be {max}")

Python's if x is not None: is the everyday equivalent — check for presence, then use the value. Rust's if let combines the check and the unwrap into one line, and it works for any pattern, not just None.

Key takeaway
if let PATTERN = value { ... } runs its block only when the value matches — a concise match for when you care about a single pattern.
13

if let else

Handle the one case, and everything else in an else

You can pair if let with an else, which covers all the patterns the if let didn't. The else plays the role of the _ arm in a match. Here's a counter that tallies every non-quarter coin while announcing quarters:

let mut count = 0;

// The match version:
match coin {
    Coin::Quarter(state) => println!("Quarter from {state:?}!"),
    _ => count += 1,
}

// The equivalent if let / else:
if let Coin::Quarter(state) = coin {
    println!("Quarter from {state:?}!");
} else {
    count += 1;   // runs for every non-Quarter coin
}

Both forms behave identically. Choose whichever reads better: a full match when you handle several cases meaningfully, if let/else when it's really "this one pattern versus everything else."

Rule of thumb: reach for match when exhaustiveness protects you (especially with enums you might extend later), and if let when a single pattern is all you care about and the check would just be ceremony.
Key takeaway
if let … else handles one pattern in the if block and all remaining cases in the else — the compact twin of a two-arm match.
